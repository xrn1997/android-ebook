## 1. 背景与目标

用户反馈"本地书籍入库时间超长"。排查结论：瓶颈不在解析，在存储模型与写入方式。

当前本地导入（`module_book/.../util/BookImportManager.kt`）对一本 3000 章的 TXT：

- 同一文件完整读 3 遍：全文件 MD5（`:52-59`）、编码探测（`:108-117`）、逐行切章（`:128-186`）
- 每章 2 次独立 DAO 调用且**全程无事务包裹**（`:206` 逐条 `bookContentDao.insert`、`:221` `chapterListDao.insertAll(listOf(单条))`）→ 约 6000 次 SQLite 事务提交
- 导入完成后 `BookImportViewModel.kt:91` 又调 `BookRepository.addToShelf`（`lib_book_common/.../BookRepository.kt:104-120`），把已全部入库的章节**再 REPLACE 一遍**
- 每个非空行现场编译一次 `"\\s*".toRegex()`（`:160-161`）

目标不是"把这套写得更快一点"，而是换掉模型：**导入耗时与文件大小解耦，同时让多格式、导出、跨源评论这三件未来事不必再改一次地基。**

## 2. 决策摘要

| # | 决定 | 拒绝的替代 |
|---|---|---|
| 1 | 正文一律**不落 SQLite**，每章一个文件；DB 只存元数据与章节索引 | 保留 `book_content` 全文入库、只做批量事务（导入仍 ∝ 文件大小，EPUB/PDF 也无法承接） |
| 2 | **本地格式与网络书源统一成一个抽象 `SourceReader`**：规则驱动与格式驱动都只是它的构造参数 | 为本地书另立一个 provider 接口（两个平行抽象，加格式时还得选边） |
| 3 | 章节内容定位统一为一个字段，`dur_chapter_url` **趁早改名 `content_ref`**（本地存相对路径、网络存 URL） | 复用旧名只补文档（一个叫 chapterUrl 却装着文件路径）；或加第二列（"内容在哪"重新变成两个真相源） |
| 4 | 正文不进 DB ⇒ `book_content` 表与 `has_cache` 列一并删除 | 保留表当网络缓存（双基座，缓存一致性义务继续存在） |
| 5 | 书目录进应用私有目录，目录名 = `book_shelf.note_url`（本地书即内容 md5），一本书一个目录 | `书名_创建时间`（书名可变→需搬目录；含非法字符；`filesDir` 对人类不可见）；`时间-md5前8`（时间戳多余，且给重导入留新目录的口子） |
| 6 | 章文件名用**序号** `c00001.txt`，不用章节名 | 章节名作文件名（标题可变、含非法字符、255 字节组件上限下中文易截断撞名、无人类读者） |
| 7 | 存储层**不清洗**，规范化全部搬到读取层 | 存储时清洗（当前实现删光行内空格、把全角缩进写进正文，不可逆） |
| 8 | 评论聚合键换成客户端派生的**不透明 token `comment_key`**，服务端只存不解释 | 服务端建作品/书籍表存书名作者（后端不得存书籍数据，法律边界） |
| 9 | **不做旧数据兼容**。判据只有一条：数据可否再生 | 双键过渡读、旧表回落、自动迁移存量 |
| 10 | **两种身份分离**：`md5` 只当拷贝身份（哪份文件、哪个目录），`comment_key` 才当作品身份（是不是同一本书） | 用 `md5` 判同一本书（同一本书不同来源的 md5 必然不同）；或让不同来源共用章文件目录（切分不一致会让索引指向错内容） |
| 11 | **一条目关联多键**：读评论取全部关联键的并集，写评论只取主键；元数据编辑是重算并切换主键的正规入口，配合导入时点的判重处置（§9.4，ADR-0023） | 单键（改元数据即丢历史评论、系统性错元数据下纠正者孤立）；只禁止重算不给修键出口（r2 的写法，等于让用户背着错桶） |

第 9 条的界线：本地书索引、网络书正文缓存都是**可再生**数据，删了重导/重下即可，背兼容没有收益；评论是**用户产生的不可再生**数据，所以键的算法版本前缀（§9）必须留。

## 3. 领域模型

```
作品（概念层，无 work_id 这类标识符）
  └── Source   来源条目 = 今天的 book_shelf 一行
        ├── 网络来源：书源规则驱动，content_ref 是该站章节 URL
        └── 本地来源：格式驱动，content_ref 是私有目录里的章文件
              └── ChapterIndex  章节索引行（序号 / 标题 / content_ref）
```

"作品"在代码与库里只以 `book_group(comment_key, note_url, is_primary)` 的形式存在——**刻意不给它 `work_id` 这样的名字**，因为一个带 ID 的"作品"实体正是后端不能持有的东西。标识只有一个：`comment_key`。

归属规则：

- **进度、书签挂 Source**。不同来源的分页位置不可互通；跨来源续读按**章序号映射**（沿用 ADR-0016 / CONTEXT.md「阅读中换源」已定的映射规则，不另发明第二套）。
- **评论挂作品**（按 `comment_key`），因此本地书第一次获得评论能力。
- 书架按 Source 显示，可折叠成一个作品。

不变式：

1. **`comment_key` 的输入是元数据，用户显式编辑元数据即重算键**（r4 修正：早先"派生只在入库时算一次、编辑元数据禁止重算"的写法作废——纠正元数据正是修对错桶的正规入口）。要守的是另一半：重算只**换主键**，旧关联行保留在并集里，否则用户一改书名，历史评论当场整桶消失。详见 §9.2、§9.3。
2. `content_ref` 的取值不再被评论关联约束（决定 8 已把它解放），因此本地书可用相对路径、重解析时可随章节重建。

**实现顺序上有一条硬依赖**：必须先做评论换键（§9），`dur_chapter_url` 才具备改名成通用 `content_ref` 的资格——它此前被两个身份同时绑住（书源章节 URL + 评论聚合键）。两步不能倒过来做。

## 4. 内容基座

```
filesDir/books/<内容md5>/
    ├── c00001.txt          章节正文，文本无损切片
    ├── c00002.txt
    └── cover.<ext>         （EPUB 内嵌图或本地同名图，可选）
```

- **目录名就是 `book_shelf.note_url`（本地书取内容 md5）**，两者同值不再另立标识。此前目录名带"首次入库时间"是多余的：防冲突由 32 位完整 md5 承担，而时间戳既不可读又给"重导入产生新目录"留了口子。时间戳只在导入期的临时目录名里用于避让并发。
- `note_url` 是 `chapter_list.note_url` 与 `book_group.note_url` 的关联列，取值必须一次定死，因此本地书 = 内容 md5、网络书 = 该书源的 noteUrl，两种来源共用同一列。
- **两种身份不要混：`md5` 是"拷贝身份"，只回答"这些章文件属于同一份内容"；"这一份和那一份是不是同一本书"是"作品身份"，由 `comment_key` 回答（§9）。** 目录名用 `md5` 只是为了保证目录名唯一且不可变，它不承担识别同一本书的职责。
- 由此推论：**同一本书的不同来源必须各占一个目录**，不共用章文件——各来源的章数、切分边界、正文里的站点杂质都不同，共用会让章节索引指向错位的内容。
- 章文件名用序号（决定 6）。导出时另生成以书名命名的产物，那是另一回事。
- **`chapter_list.content_ref` 对本地书存自包含的完整相对路径** `books/<note_url>/c00001.txt`，读取方拿到就能用、不再回查书级字段。**不设 `local_dir` 列**——目录名就是 `note_url`，再加一列等于给同一件事两个标识，两者迟早漂移。
- **导入过程中目录名带 `.tmp` 后缀，全部写完才改名**。否则进程被杀留下半本书，而对账无法区分"半成品"和"完整书"。改名是"这本书可用"的唯一提交点。
- `BookLocation`（目录相对路径 + 格式）是"一本书内容仓库在哪"的定位值类型，reader 只认它，不认 `File` 也不认 `Uri`——§13 的 SAF 迁移将来只换这个类型的构造方式。
- 一本书一个目录。删书 = 删目录 + 删索引行。缓存完整性靠对账（DB 无此目录 → 删文件；目录存在但 DB 无书 → 删目录），逻辑集中一处。
- **存储层不清洗**：换行、BOM、缩进、空白折叠全在读取层做。"发现规则定错了"永远是改一行读取代码，而不是"数据已损毁"。
- **章文件统一重编码为 UTF-8**：无损指的是**文本层**（字符一个不少），字节层归一成 UTF-8，这样读取层不需要再管源编码，`text_charset` 只在切分与重解析时用到。
  **解码必须严格**：用 `CharsetDecoder` 并将不可映射字符策略设为 `REPORT`，探测出的编码解不动就直接判导入失败。**禁止 `REPLACE`/静默替换**——把 GBK 里解不出的字节换成 U+FFFD 是又一种不可逆损毁，而且它不报错、只让书里悄悄出现问号，正是本次要根除的那类 bug。
- 原件不保留：章文件即"切分后、清洗前"的无损形态。唯一救不了的是章节边界切错，那靠重新导入。

## 5. 数据模型与迁移

`AppDatabase` 当前 version = 2（`lib_ebook_db/.../AppDatabase.kt:28-39`，链见 `di/DatabaseModule.kt:34-49`）。因 M1 拆成两期（§10），迁移分两步，同一迁移内不做两次身份变更：

**v2 → v3（M1a）**

```
新增 book_group(comment_key TEXT NOT NULL, note_url TEXT NOT NULL, is_primary INTEGER NOT NULL,
                PRIMARY KEY(comment_key, note_url), INDEX idx_book_group_note_url(note_url))
book_shelf   + book_format TEXT NULL, text_charset TEXT NULL,
             match_name TEXT NULL, match_author TEXT NULL
chapter_list : dur_chapter_url  RENAME TO content_ref      （主键语义不变，仍是自然键）
删除本地书的 book_content 行（tag='loc_book'）与 tag='loc_book' 的书架行
```

**v3 → v4（M1b）**

```
删除 book_content 表
chapter_list - has_cache
```

- `book_content` 与 `has_cache` 都不能在 v3 删除：网络书的正文要到 M1b 才出 DB，M1a 期间它仍是网络书的缓存事实源，而下载面板的"已缓存 y/z"徽章仍读 `has_cache`。v3 只清本地书那份；**本地书的章节行在 M1a 期间 `has_cache` 填 `false` 且无消费者**（下载与覆盖率路径都按 `LOCAL_TAG` 排除本地书，见 `DownloadRepository.kt:53,69`），v4 再与表一并收掉。
- M1a 期间本地书的缓存存在性判定已经改走"章文件在不在"，`has_cache` 只对网络书保有意义，两种基座并存的窗口期到此为止。
- v3 里 DDL 是示意：`note_url` 上的索引由 Room `@Index` 表达；「一个 `note_url` 恰好一行 `is_primary=1`」SQLite 与 Room 都无部分唯一索引可表达，由 DAO 在 `withWriteTransaction` 内保证（§9.2）。`book_group` 在 M1a 建表**并且入库时就写关联行**（`comment_key` 先存着不被消费），M2 只做消费与合并/拆分——否则 M2 还得给 M1a 期间入库的书补一次键回填。
- 列改名用 `ALTER TABLE chapter_list RENAME COLUMN dur_chapter_url TO content_ref`（SQLite 3.25+ 支持），实体字段 `durChapterUrl` 同步改名 `contentRef`。
- **删 `book_content` 连带丢弃网络书已下载的正文**，用户需重新下载；`tag='loc_book'` 的存量书架行直接删、不回填。两者都属可再生数据（决定 9）。
- `has_cache` 与 `book_content` 本是同一事实的两个真相源，此前已产生"有正文但目录显示未缓存"的一致性义务（`BookContentDao`、`ChapterListDao` 的 KDoc 各记载一处）。合并成"章文件在不在"之后，这个不一致类整体消失。
- 遵守 ADR-0003 的迁移纪律：每步 version +1、链上追加紧邻的 `MIGRATION_2_3` 与 `MIGRATION_3_4`、不跳版、不删旧迁移、分别提交 Room 生成的 `3.json` 与 `4.json`、**不启 `fallbackToDestructiveMigration`**。

## 6. 导入流水线

```
选文件 → 拷贝进 filesDir/books/<md5(拷贝中)>.tmp/，同一次流式读里喂 MessageDigest 算 md5
      → md5 已入库？ 是 → 删临时副本，返回"重复"（零解析、零写入）
      → 后台协程：扫一遍求章节边界 → 逐章写章文件 → 一次批量事务写 book_shelf + book_info + 全部索引行
      → 目录改名去 .tmp → 发事件刷新书架
```

- **前台只付"拷贝"的代价**，切分与落库全在后台。点完导入即可继续操作，该书在书架上显示"解析中"。
- **入库时从文件名解析书名与作者**（当前是 `BookImportManager.kt:81` 直接把文件名去扩展名当书名、`:87` 硬写作者占位）。这一步是作品身份的前提：`comment_key` 由书名+作者算出（§9），作者恒为占位会让键**既误并又分裂**——两本同名不同作者的书算出同一个键，而同一本书的两种文件名写法（`星辰变.txt` 与 `《星辰变》我吃西红柿.txt`）算出两个键。解析模式参照常见命名（`书名《X》作者：Y`、`X 作者：Y`、`X by Y`），全部落空才退到占位。
  **必须在本期做**：键一旦开始积累评论数据，事后补解析只能改善新书，旧数据的桶已经错了。
- MD5 在拷贝那一次读里顺便算完，省掉当前那次独立的全文件读。
- 批量写用 `RoomDatabase.withWriteTransaction`（`androidx.room3` 3.0.0 提供，room3-runtime sources `RoomDatabase.kt:662`）。全仓业务代码目前零使用事务，这是第一处。
- 重复检测两级：**精确 = 内容 md5**（同一份文件重导由 `LocalBookImporter` 短路，不产生任何写入）；**模糊 = `comment_key` 命中书架某条目的当前主键** → 在导入时点弹四动作处置框（继续添加 / 智能合并 / 覆盖 / 跳过），不再做事后 SnackBar。处置一律**先导入新条目、后处置旧条目**（反过来时导入抛异常就是两头空），覆盖删旧之前先 `absorbGroupKeys` 吸收旧条目的关联键。语义与取舍见 §9.4 与 ADR-0023。
- **性能数字目前只有量级推演，没有实测**（6000 次事务 → 1 次事务 + 顺序文件写）。M1a 的第一个任务是在真机上量出改前/改后基线，回填本节。改前基线夹具（`module_book/src/androidTest/java/com/ebook/book/ImportBaselineTest.kt`，2000 章 / 约 6MB UTF-8 TXT，走真实导入链路）已就位，**待人工执行** `./gradlew :module_book:connectedDebugAndroidTest -Pandroid.testInstrumentationRunnerArguments.class=com.ebook.book.ImportBaselineTest` 并从输出的 `BASELINE elapsed=… chapters=… fileKb=… memDeltaKb=…` 行回填，本节在此之前不填任何具体数字。
- `ReadBookActivity.openBookFromOther`（外部打开，`ACTION_VIEW` + `text/plain`）走同一条流水线，不再单独写一份。

## 7. 统一来源抽象

放 `lib_book_common` 的 `com.ebook.common.analyze`（`BookRepository` 所在层，接缝不能让业务模块持有）：

```kotlin
interface SourceReader {                                  // 一个来源 = 一本书的内容从哪来、怎么解析
    suspend fun readMetadata(ref: SourceRef): BookMeta
    suspend fun buildChapters(ref: SourceRef): Flow<ChapterEntry>
    suspend fun readChapter(ch: ChapterEntry): ChapterContent
}

sealed interface SourceRef {
    data class Local(val loc: BookLocation, val charset: String?) : SourceRef   // 格式驱动
    data class Web(val rule: BookSourceRule, val noteUrl: String) : SourceRef   // 规则驱动
}

ChapterEntry(index: Int, title: String, contentRef: String)
ChapterContent(title: String, paragraphs: List<String>)
```

实现：`TxtSourceReader`、`EpubSourceReader`（M3）、`JsoupSourceReader`（由现有 `JsoupBookParser` 的目录与正文部分改造）。

- **"书源规则"与"本地格式"在这里是同一件事**：都是"从哪读、怎么读出来"的构造参数。发现类能力（搜索/分类/书城）不属于本接口，留在 `BookParser`——所以 **M1b** 的动作是把 `BookParser` 的 7 个方法**拆成「发现」与「内容」两半**，本地来源只实现后者（M1a 只新增接口与本地实现，不动 `BookParser`）。
- `readChapter` 返回**段落列表**而非裸 String：EPUB 的 `<p>`、PDF 的文本块、TXT 的 `\n` 段都能自然映射，段评锚点也直接挂在这里。签名若是 `String`，接 EPUB 时就得先破签名。
- `buildChapters` 返回 `Flow`：进度、取消、恒定内存天然获得，EPUB 不必先全量解包。
- 目录规则是**数据不是代码**：`第.{1,7}章.*` 从 `BookImportManager.kt:106` 的硬编码挪进 reader 的规则集，可被用户导入的规则覆盖（本期只做规则可插拔，不做管理 UI）。
- 编码探测结果**存进 `book_shelf.text_charset`**，不再每次导入重头探测。

内容路由按 `tag` 选出 `SourceRef.Local` 或 `SourceRef.Web`，`ReadBookActivity.loadPage`（`:269-279`）"取内容 → 用"的结构不动，只换实现。这顺带根治一个现存缺陷：本地书内容缺失时，`BookReadViewModel.kt:120-128` 会拿 `md5_章号` 当 URL 去打第三方书源。

**必须有一层章节内容内存缓存**（r5 补）：`loadPage` 是**每翻一页都取一次正文**，而 §8 的规范化也在取内容时跑。正文原先在 DB 时这只是一次主键查询；改成章文件后，没有缓存就等于每页都 open + read + 解码 + 规范化一遍。所以 `SourceReader` 之上要有个按 `content_ref` 为键的小容量缓存（当前章 + 前后各一章足够，翻页场景全覆盖），并在字号/排版无关的维度上复用——排版偏移本身是另一层可缓存的派生数据（`ReadBookActivity.kt:281-293` 的注释已经自认"每页整章重排"是会放大的开销）。M1a 需同时定下这两层的失效条件：换来源、改字体字号、章节重解析。

## 8. 规范化规则

存储侧不清洗（§4），读取侧规则集中成一个可单测的纯函数：

- 统一换行为 `\n`（`ReaderTypesetter` 依赖它作段落分隔）
- 去 BOM
- 行内连续空白折叠为**一个**空格——不再删光。当前 `.replace(" ", "")` + `.replace("\\s*".toRegex(), "")`（`BookImportManager.kt:143-144,159-161`）会永久销毁 `1 000`、英文书名、代码里的空格，而 ADR-0017 第 21 行原打算让 EPUB 沿用此约定，会把损毁复制进新格式。
- 段落首行缩进 `　　` 由渲染层补，不进存储（当前是 `:171` 把它 append 进正文，`ReaderTypesetter` 再原样丢给 `StaticLayout`）。渲染层补缩进时须先吸收行首已有的全角/半角空白。
- 默认作者显示词由「佚名」（`BookImportManager.kt:87`）改为「侠名」。**这个字面量不参与 `comment_key` 计算**（§9），否则改这一个词就等于给所有这类书换了评论桶。

## 9. 评论标识

### 9.1 键的派生

问题：现在评论按 `chapter_url` 字符串聚合，后端不消费、只当桶键。后果是不同用户用不同书源就对不上；本地书的 `md5_章号` 只有本机认得；书籍级评论靠一个**无索引的 `BookName` 文本列**聚合（`ebook-server/backend/model/comment.go:22-23`）——实际已失效。

方案：桶键换成客户端派生的不透明 token。

```
comment_key = "ck1:" + sha256( 归一化(书名) \0 归一化(作者) )
章评键      = comment_key + "#" + 章序号
段评键      = 章评键   + "#" + "pa1:" + 段落下标 + ":" + 该段规范化后前 16 字的哈希
归一化      = 去书名号、折叠空白、全角转半角、转小写；作者为空（含"佚名""侠名"这类占位）归一为空串
```

段评锚点**同样要带版本前缀**（`pa1:`）：它建立在 §8 的规范化之上，规范化一改（比如繁简转换、空白折叠规则调整）所有锚点全变、段评整体散桶。这与 `ck1:` 是同一类风险，只给书名作者版本化而漏掉锚点是半个防护。

作者**参与**哈希（同名不同书靠它区分），但**占位词不进哈希**：作者缺失时归一为空串、键退化为只用书名，这样默认显示词随便换，键空间不动。

服务端只加一列 `comment_key text index`，查询按它过滤；不存书名、不建书籍表、不提供"列出所有书"。**这比现状更合规**：sha256 不可逆、渲染不出书名、列不出目录，而今天明文存着 `BookName` 与 `ChapterName` 两个 200 字文本列。

### 9.2 一个条目关联多个键

```
book_group(comment_key, note_url, is_primary)   一个 note_url 可有任意多行
读评论 = WHERE comment_key IN (该条目的全部关联键)
写评论 = 只用 is_primary 那一行的键
合并 = 加一行    拆分 = 删一行    改元数据 = 换主键（旧行原样保留）
```

单键方案下这三件事凑不到一起，多键可以：

- **纠正元数据不丢历史**：换主键后旧键仍在并集里，用户既看得到自己以前写的，新评论又进对的桶。
- **接住系统性错元数据**：某书源给的书名/作者本身就是错的，多数用户共用那个错键。单键下先纠正的人反而孤立；多键下两个桶都在他的并集里——存量看得见、新评论进对桶，群体随纠正逐步收敛。
- **合并与拆分对称**：都是纯表操作，不需要任何"改别人数据"的能力。

「一个 `note_url` 恰好一行 `is_primary=1`」SQLite 与 Room 都表达不了（无部分唯一索引），由 DAO 在事务内保证。

### 9.3 元数据编辑是修正键的正规入口

取代 r2 里"编辑元数据不得重算键"那条不变式（见 §3）：重算键不是要防的事故，它就是功能本身。要配套的是旧评论的去向。

- 用户改主匹配名或匹配作者 → 重算派生键 → 设为新的 `is_primary`，旧关联行保留。
- **迁移自己的旧评论**：`UPDATE comments SET comment_key = ? WHERE user_id = 本人 AND comment_key = ?`。只动本人行，不需要管理员权限。
- 他人评论一律不搬。UI 必须写明「你的 N 条评论已随之迁移；该桶内他人评论不会移动」，否则是一个隐藏期望差。
- 全局性的桶污染（错键上已有大量他人评论）靠管理员级 `rehash` 兜底：服务端只做不透明 token 的 `UPDATE ... SET comment_key = ? WHERE comment_key = ?`，不接触书籍语义。
- 手动入口不止一个改名框：**键是算出来的，就得让用户看得见输入项**，否则它是魔法、错了无法 debug。面板含主匹配名（默认书名）、匹配作者（可空）、当前主键、已关联的其他键列表（合并历史）。
- 匹配名与显示名是**两回事，分开存**：`book_shelf.match_name` / `match_author` 两个可空列，为空时回落到 `book_info.name` / `author`。显示层永远用显示名，只有算键用匹配名。不分开就会出现"为了对上评论把用户看到的书名改掉"这种污染。
- 主匹配名/匹配作者**同时是导入判重的输入**：判重比的是它们算出的当前主键（`book_group` 的 `is_primary` 行），不是 `book_info.name`。所以在这个面板改一次匹配名，改的是"这本书以后算哪个键、以及下次导入同作品时会不会被认出来"两件事。

### 9.4 重复判定（原「自动合并算法」，已由 ADR-0023 改写）

先划边界（不变）：**判定是本机行为，键是全局契约**。判定只负责把"你书架上这几个条目"归到同一个键下；跨用户聚合靠所有人算出同一个键，不靠算法。

**五信号打分与三档阈值已撤销**（章名序列相似度 / 段落指纹 / 章数接近 / 书名 / 作者 → `BookMergeScorer`，代码与测试已删）。撤销的根因是**输入侧**：两个强信号都要求先把书切完章，而判定必须发生在导入之前——切一遍 2000 章的文件只为判断"是不是同一本"，代价与收益不成比例。剩下的书名+作者两个中信号恰好就是 `comment_key` 的两个输入项：精确键既然已经算得出，模糊打分就是在用概率方法重做一件已有确定解的事。取舍与代价详见 ADR-0023 的「权衡」。

现在的口径：**判重 = 待导入文件的 `CommentKey.compute(标题, 作者)` 等于书架某条目的当前主键**，命中即在导入时点弹处置框（不做事后 SnackBar）。四个动作：

| 动作 | 语义 | 破坏性 |
|---|---|---|
| 继续添加 | 两条目共存，同键 → 评论读并集天然共享 | 无 |
| 智能合并 | 新条目多出的**尾部章节**补进旧条目（旧条目进度/键全保留），新条目退场 | 低 |
| 覆盖 | 新条目替换全部命中旧条目，删之前先吸收旧条目的 `book_group` 键 | 高 |
| 跳过 | 本文件不导入 | 无 |

「继续添加」就是本节原设计想要的非破坏默认——同键共存是 §9.2 这套模型支持的正常形态，不是需要抹平的缺陷。

已知救不了的情况（沿用原判断，只是不再有算法兜底）：同名且都无作者的两本不同的书会算出同一个键而被判重；作者解析结果两边不一致的同一本书则**不会**被判重（宁可漏提示，不可误并——命中即给出会删条目的按钮）。两类都归 §9.3 人工纠正。

### 9.5 三条固有约束

1. **`ck1:` 算法版本前缀保留。** 保护的不是旧版本用户，是评论这份**不可再生**数据：归一化规则哪天改（比如加繁简转换），会让不同版本客户端静默算出不同键、两堆评论互不可见，而这只在有真实用户后才暴露。改归一化 = 改键空间 = 破坏性变更。
2. **跨来源章序号对不齐**是这套模型的固有软肋（切分规则不同、站点多出"作者的话"）。取"按章序号 + 相邻章容错显示"，不取章节标题哈希（跨源标题形态差异更大，且进度映射已用章序号，两套对齐规则会分裂）。
3. **键由客户端算，意味着任何人都能把自己的评论塞进任意书桶**（改个书名即可）。这不是本设计新引入的——今天 `chapter_url` 同样随便填且服务端明确不校验。它是"后端不存书籍"这条边界的必然推论：没有权威注册表，就没有权威键校验。能做的防线在内容层（举报、信誉、黑名单），不在键层。

## 10. 里程碑

共用同一套表和列，任何一期都不预留"下一期要推翻"的东西。

- **M1a 本地书基座与导入流水线**（这一期就把"入库超长"解决掉）：真机性能基线 → Room v3（建 `book_group`、加 `book_shelf`/`chapter_list` 各列、`dur_chapter_url` 改名 `content_ref`、删 `has_cache`）→ 章文件读写与对账、章节内容内存缓存 → `SourceReader` 接口与 `TxtSourceReader` → 导入流水线（拷贝即哈希 + 文件名解析书名作者 + 严格解码 + 后台切分 + 批量事务 + 写 `book_group` 关联行）→ 规范化搬到读取层 → 本地书内容路由按 tag 分叉。
  **人工装机验证项**：导入大文件不卡前台、本地书翻页与进度、重复导入拦截、进程被杀后 `.tmp` 目录不残留成有效书。
- **M1b 网络书出 DB 与抽象统一**：`book_content` 表删除、网络书缓存改写章文件、`BookParser` 拆「发现 / 内容」两半、`JsoupSourceReader`、下载服务与缓存对账改造。
  **人工装机验证项**：离线下载断点续跑、缓存覆盖率展示、从书架移除后文件回收、下载中断的文件残留。
  拆在 M1a 之后的理由：`SourceReader` 与 `content_ref` 已在 M1a 定死，M1b 只是给网络书换一种写入落地，不改契约、不改阅读器读取路径。
- **M2 来源分组与评论**：消费 `comment_key`、**导入时点判重与处置**（继续添加 / 智能合并补尾章 / 覆盖 / 跳过，见 §9.4 与 ADR-0023；原计划的五信号自动合并打分与书架侧 SnackBar 已撤销）、**拆分**（删关联行）与**修键面板**（主匹配名/匹配作者/当前主键/已关联键列表，入口在书籍详情页）、评论读写换键（读并集、写主键）、**本人旧评论迁移接口**、服务端加 `comment_key` 列并支持 `comment_keys` 数组过滤、书籍级评论按主键聚合、旧键评论自然废弃。
- **M3 多格式**：`EpubSourceReader`（`java.util.zip` + jsoup，均为既有运行时能力）、封面导出、扫描白名单扩 `epub`、目录规则可导入。

- Room `MIGRATION_2_3` 与 `MIGRATION_3_4` 测；`content_ref` 改名的编译期回归（全仓引用点必须清零）
- 严格解码测：探测编码与实际字节不符时必须判导入失败，**不得**产出含 U+FFFD 的章文件
- 章节内容缓存测：翻页不重复读盘、换来源/改字号/重解析三种失效条件各自生效
- 性能基线：真机测改前/改后导入耗时与峰值内存，回填 §6

| 章文件是"原字节切片"还是"重编码文本"没定 | 读取层是否还要管编码不明确；若顺手用 `REPLACE` 解码策略，会把不可映射字节静默变成 U+FFFD——又一种不报错的不可逆损毁 | §4 §5 §11，定死统一 UTF-8 + `REPORT` 严格解码 |
| 目录名带时间戳、而 `note_url` 取值一直没定 | 同一件事两个标识，时间戳还让"移除后重导"产生新目录 | §4，目录名 = `note_url` = 内容 md5 |
| 正文出 DB 后没有内存缓存层 | `loadPage` 每翻一页都读文件 + 解码 + 规范化，比原来的一次主键查询更差，且叠加"每页整章重排"的已知放大 | §7 §11，加章节粒度缓存与三种失效条件 |
| 段评锚点没有算法版本前缀 | 规范化规则一改，锚点全变、段评整体散桶；`comment_key` 有 `ck1:` 而锚点没有，是半个防护 | §9.1，锚点加 `pa1:` |
| 匹配名与显示名未分字段 | 会出现"为了对上评论而改掉用户看到的书名"这种污染 | §9.3 §5，`match_name`/`match_author` 独立可空列 |
| `book_shelf.local_dir` 与 `note_url` 同指一件事 | 定死目录名 = note_url 后，这一列成了第二个标识，两者迟早漂移 | §4 §5，删列，目录路径由 `note_url` 派生 |
| M1 体量过大且与"一次迁移到位"冲突 | 拆不动也验不动 | §10 拆 M1a/M1b，§5 迁移随之拆成 v3/v4 两步 |

**一处我已按推荐写进正文、但你可能推翻的取舍（§9.4 命中之后的默认权限）**：判重命中时，是把切换 `is_primary`、补章合并这些动作留给用户一次点击（零污染风险，代价是每次多一下确认），还是自动替他合并（跨来源写侧评论真正聚合，但一旦误合，用户的评论就被写进了别人书的桶，属全局污染）。

正文按前者写了，理由是**两类错误的可逆性不对等**：读错了只是看见多余评论，本地可撤销、不伤别人；写错了是往共享桶里灌内容，要管理员 `rehash` 才能收拾。而且导入时点那次四选一的处置框本身就是一次显式确认，用户成本几乎为零（原设计的书架侧"轻确认"通知已随 ADR-0023 撤掉，确认时点前移到创造重复的那一刻）。你若认为这一步该全自动，改 §9.4 的处置表即可，其余各节不受影响。
