# 阅读恢复：以「会话标记残留」判定上次异常终止，启动页据此直接落回阅读界面

应用上次没正常收尾（进程被划掉、前台强杀、崩溃、被系统回收）时，下次启动由启动页直接打开
上次那本书的阅读界面；用户**主动退出**阅读界面（按返回等）则不受影响，下次启动照常进主页。
判定依据是一个本地标记：阅读界面**成功打开某本书**时写下该书 `noteUrl`，**正常退出**时清除——
于是「标记还在」恰好等价于「上次属异常终止，且当时在读某本书」。恢复精度是**章级**，不保证页。

## 动机

进程被划掉或强杀时，`onDestroy` 不会执行，`onPause` 也可能不执行（Android 只保证「进程被回收
前已创建的 Activity 至少调用过一次 onPause」的弱承诺，而 force-stop 与崩溃不给任何回调）。
阅读进度因此分两种情况：**日常「划掉」多半发生在应用已切到后台之后**，那一刻 `onPause` 已经
把进度落过库，库里是新的；而**前台强杀与崩溃**时进度停在更早一次落库的位置，会落后几章。
两种情况下启动侧都无从知道「用户上次停在阅读界面」，一律进主页 —— 用户得重新找书、翻回原处。

同时要说清本决策**不解决**什么：进度本身的写入时机没有改动（仍在 `onPause`）。本决策只回答
「启动后落到哪个界面」，不承诺「恢复到上次看到的那一页」。

## 决策

1. **标记的写与清都由阅读器负责，语义是「会话未收尾」**。
   写入点覆盖「当前读的是哪一本」的每一次变化：应用内点书、应用外导入打开、换源成功（`noteUrl` 会变，
   不跟着换会让恢复去查一个已被换源事务删掉的旧条目）。清除点是 `onDestroy` 且 `isFinishing`
   —— 判据必须是 `isFinishing`，因为旋转重建、系统回收也会走 `onDestroy`，但那不属于「用户离开了
   阅读界面」，重建后用户还在读同一本书，标记必须留下。
   由启动页负责写是行不通的：启动页只可能出现在「下一次启动」，而正常退出那条路径（进程还活着）
   根本没有写入方，标记会永远停在上一次异常终止的旧值上，表现为「之后每次启动都被拉回阅读界面」。

2. **标记只是「可能过期的断言」，恢复前必须回库复核**。
   标记记的是 `noteUrl`，而用户完全可能在那之后把这本书从书架删掉（或换源换掉了 `noteUrl`）。
   复核不通过就顺手清标记并走主页——留着它只会让之后每次启动都白跑一趟查库。
   复核用「书架行 + 书籍元数据 + 章节列表」的完整查询，不能只查书架行：`bookInfo` 与 `chapterList`
   在实体上是 `@Ignore` 字段（不落库），按行查询拿不到，章节列表为空会让阅读器渲染成**空白页**
   ——这条路径不闪退、不报错，只有装机才看得出来。

3. **跨模块跳转用 TheRouter 建 Intent，但由启动页自己 `startActivity`，且不用 `matchRouteMap` 探测路由**。
   启动页在 `module_main`、阅读器在 `module_book`，功能模块互不依赖，只能经路由跳转。
   但 TheRouter 的路由表是**异步**加载的（`RouteMapKt.asyncInitRouteMap` 走 `TheRouterThreadPool`），
   启动页此刻查不到路由，既可能是「这条路由真的不存在」（`module_main` 独立运行时的形态），
   也可能只是「还没加载完」。拿它当开关，会把后一种情况一并判成「不可恢复」而静默跳过——
   功能看起来没生效，日志里还留着一句误导的「没有阅读器路由」。
   改为：先 `startActivity(MainActivity)` 垫底，再用 `createIntent(ctx)` 拿 Intent、判 `component`
   非空后自己启动。路由没落地时 Intent 没有落地页，用户安静地落在主页（不白屏）；落地了就落回阅读器。
   这样两条路都不依赖路由表的加载时机，也不需要 `ActivityNotFoundException` 之外的兜底。
   （`createIntent` 而非 `navigation()`：后者不给「是否落地」的反馈，而这里必须能区分成败。）

4. **主页垫在阅读器下面**（先启动 `MainActivity` 再启动阅读器）。
   视觉上仍是「直接从启动页落到阅读界面」，但用户按返回是回到书架，而不是退出应用——阅读器
   （`launchMode="singleTask"`）不该是任务栈的根。

5. **不新增「翻章即落库」**。
   日常划掉有 `onPause` 兜底，进度已经是对的；为覆盖前台强杀/崩溃而在翻页路径上加写库，
   换来的只是一章之内的精度，却把写库频率从「进出一本书几次」抬到「每翻几屏一次」。
   取舍见「遗留」。

## 权衡

- **被拒：用 `matchRouteMap` 探测路由可用性**——理由见决策 3。探测的诱惑在于「一行判空就能防白屏」，
  但它把「时序不确定」当成了「事实不存在」，代价是核心功能在真机上随机失效。
- **被拒：启动页用显式类名 Intent（`setClassName`）直接启动阅读器**——能同时绕开路由表的加载时机
  与「独立运行没有路由」两个问题，但把跨模块跳转从路由契约降级为字符串类名（改名不报编译错），
  且偏离本仓「跨模块导航统一走 TheRouter」的约定。现方案（路由建 Intent + 自己启动）在
  「不依赖探测时机」这一点上等价，同时保留路由契约。
- **被拒：恢复时把实体装进 Bundle 传过去**（`BookShelfEntity` 是 `Parcelable`）——`chapterList`
  动辄上千条，撞 binder 的 1MB 事务上限就是 `TransactionTooLargeException`，且只在长篇书上复现。
  传 `noteUrl` 让接收方现取，还顺带拿到「这本书是否已被删掉」的最新事实。
- **被拒：页级精确恢复**——需要翻页即落库（见决策 5 的代价），且页级位置在排版参数变化
  （字号、翻页方式、屏幕尺寸）后本来就会漂移，跨启动恢复的「精确」是假象。

## 遗留

- **前台强杀/崩溃时进度可能落后**：库里是更早一次落库的位置，恢复落在那一章而非用户实际读到的那一章。
  想收紧就得回到「翻章即落库」，本决策刻意不做（低频场景换高频写库，不划算）。
- **不保证页**：见权衡第四条。恢复落点是书架条目上记录的章与页，页可能因不再匹配而钳到该章可见范围内。
- **「跳过」按钮路径的降级**：用户若在闪屏极早期点「跳过」，可能早于路由表异步加载完成，此时
  恢复会降级为进主页（不白屏、不报错）。门控路径（等最小展示时长 3 秒）不受影响。
