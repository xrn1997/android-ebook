# 目录重抓只接受纯追加，结构分叉即整笔放弃

书架上的网络书按需重抓目录时，只有「本地每一章都还在远端目录里、且相对顺序一致」才把远端多出的
尾部章节追加进库；首章就对不上、本地有远端已无的章、或相对顺序变了，一律整笔放弃 —— 本地目录
一行不动，只在详情页留一句「请换源或重新导入」。

**理由**：章文件按序号命名（`filesDir/books/<bookId>/cNNNNN.txt`），序号一旦漂移就会静默读错章
—— 用户点第 50 章读到的是旧的第 50 章，不报错、不闪退、页面上一切正常。已下载的章与目录之间的
对应关系没有第二份事实源可以校正它，所以宁可放弃一次更新，也不做一次可能错位的合并。

**被拒的方案**：①章名兜底再比一轮（能自愈「站点只换了 URL 规则」这一类，但序号仍可能漂移，
连带要写一套章文件重命名）；②整本替换 + 章文件按新序号重建（彻底自愈，但替换瞬间正在阅读的
那一章会失配）。两者都是把一次低频的站点改版，换成高频路径上的静默数据损坏风险。

**判定为什么按 `content_ref` 定位而不是逐位比对**：远端行的 `durChapterIndex` 是 parser 按位置
连写的（两个 parser 都写 `chapters.size`），而本地序号可能有洞（用户删过章）。拿位置硬比会让一本
删过章的书**永远**判成分叉、再也追不了更，而它其实完全满足「只追加、不动既有章」的安全条件。
按 `content_ref` 定位后删除过的书仍能正常追加，安全性一分不减。

**落库时的三条口令**：新章序号从 `max(dur_chapter_index) + 1` 起，不能用 `size`（有洞时两者不等，
用 `size` 会覆写既有章文件）；远端行自带的序号**不可沿用**，必须重排 —— 否则有洞时两行会撞同一个
index，而主键是 `content_ref`，撞号既不报错也不闪退。
**第三条（撞主键即放弃）**：算出的 `tail` 若与本地既有 `content_ref` 重合、或 `tail` 内部自撞，
整笔判 `Diverged`（`ChapterTocDiff` 的判定规则 5）。撞键落库不报错，只会把既有那一行搬到表尾
（序号静默错位）或让两行互相吃掉（凭空少一章），而调用方数出来的条数还比库里多。
两个 parser 正常都会用 `seenRefs` 去重，走到这条分支说明清单本身自相矛盾；因为详情页现在也会落库，
污染不再只留在内存里，所以这道守卫从「可选」变成必须。

**目录的单一事实源是 `chapter_list`，谁要渲染或写进度都回读库里那份**（2026-09-14 落地）：
`book_shelf.dur_chapter` 存的是**列表位置**，书架的「读至」与阅读器打开第一页都按
`chapterList.getOrNull(durChapter)` 读回。写这个位置的人（阅读器）用的却是**调用方交进来的**那份目录
—— 详情页的搜索入口把源上的远端目录整个放进状态并原样交给阅读器，而那条路径从不写 `chapter_list`。
于是本地只要落后远端一章，阅读器内存里的目录就比库里长一章，写回的位置在书架侧越界：「读至」变空白、
点进去提示章节加载失败，而用户手动再跳一次最新却好了（那一次的目录换成库内条目）。末章触发追更时差额
还会翻倍：落库按库内口径 `max+1` 追加，内存拼的是「远端目录 + 追加行」，两个基数不同，目录里于是
长出两遍末章。

处方分两步：**①「抓 + 落」拆成两半** —— 判定与落库收进 `appendRemoteChapters(bookShelf, remoteChapters)`
（不发网络、本地目录在抓完之后才读，避免与并发的末章追更撞 `content_ref`），
`syncChaptersFromSource` 只剩限频 + 取源 + 抓目录 + 交棒；于是详情页能为它**已经抓到的**那份目录落库，
不必为落库再翻一遍目录页。**②调用方一律回读 `getStoredChapters`** —— 详情页（两个入口）与阅读器
追更后都改用库里那份渲染、也按它写进度；`Appended` 只带新增的那几行，够报条数，不够拼目录。

**落库前先认归属**：`inShelf` 只按 `note_url` 匹配，而多源共存下同一 `noteUrl` 可能从另一条源的搜索
结果被打开。这时手上那份是**别人家的目录**，一行都不该写 —— 不只是因为 diff 判不出纯追加（它确实判
分叉、一行不写），更因为落库那半截会把「检查得出分叉结论」写进 `final_refresh_data` 并弹一条本地目录
已失效的提示条：占掉的是这本书自己的检查窗口，说的是从没发生过的坏话。故比较 `书架行的 tag == 本次
解析用的 tag` 才落库；不同源时页面仍改用库里那份（本地实际可读的那几章）。

**被拒的方案**：`inShelf` 时干脆只把库内条目交给阅读器、页面仍展示源上那份。它同样能止住越界，
但把「页面上点得到、进去却说没有这一章」留在了产品里 —— 用户从搜索进详情看到 200 章、点最后一章，
阅读器只会提示加载失败；而且目录条数两处不一致这件事本身会变成下一次改动的前提，所以选落库而不是选隐藏。

`saveProgress` 保留**第二道**防线：写库前按 `chapter_list` 的行数钳住 `durChapter`（就地改，调用方与
`ProgressUpdated` 消费方看到同一个值），真的钳动了就留一条 `Logger.w`。它兜的是今后新长出来的
「调用方自己拼目录」，不是本处方的替代品 —— 用例里以「`durChapter` 没被钳动」断言分叉没有复发。
**库里零行时它不出手**：零行没有「最后一行」可钳，钳与不钳书架都解析不出那一章，而提前钳成 0 会误伤
一条正常路径 —— 从搜索直接开读（还没加书架）时 `chapter_list` 是空的，用户读到第 100 章点
「加入书架」，加书架会连带把那份目录整本写进库，那个位置当场有效；钳过的话进度就被抹回第一章。
