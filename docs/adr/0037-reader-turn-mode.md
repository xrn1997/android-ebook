# 翻页方式：上下滚屏与左右翻页共用同一条分块链

阅读器新增「上下滚屏」翻页方式，与既有左右翻页并列（设置面板「翻页方式」二选一，落 SP）。两种方式的正文由**同一条排版分块链**给出，差别只在容器：左右翻页是三页窗口 + 横向拖拽，上下滚屏是**跨章连续的一条竖向列表**（章段 = 标题项 + 屏块项）。进度口径两边都是「章内第几屏」，因此零 schema 改动、换方式可按行号换算落点。

## 决策

1. **滚屏模式仍按「屏」记进度**：`dur_chapter_page` 在两种方式下都写「章内第几屏」，不新开一个「滚动偏移」列。理由是进度落库口径不随翻页方式变——换方式时只需按行号换算一次落点，冷启动读回时该值与已持久化的方式天然同口径，不必判断「这条进度属于哪种方式」。代价是滚屏的「屏」不是物理屏幕而是**排版块**：块内不含章节标题行与页码行（标题是章段开头会滚走的分隔项、页码是视口外的常驻行），故块比翻页模式的屏高、每屏行数更多。
2. **两种方式共用分块链，不各写一套**：断行（`ReaderTypesetter`）→ 每屏行数（`pageLineCount`）→ 按行偏移切原文子串（`loadPage`）这条链只有一份，两端只负责各自的容器几何。理由是「分页与渲染必须同源」是既有契约，两套切法必然长出「上一屏与下一屏接不上」那类静默错乱；加载去重与三态也随之下沉为共享的 `ReaderPageStore`。**两端连续阅读都会跨章累积已加载页，故都按各自几何裁剪保留集，差别只在半径的单位**：翻页的几何就是三页窗口（它在章首/章末把窗口指向**相邻章**、翻页提交又不经 `clear`），裁到窗口的三个键；滚屏的列表跨章连续，按**块**半径裁是错的——同章内回滚会把刚读过的块丢掉、重走一遍加载并在 UI 上闪一下转圈（实测 0→6→0 往返，7 块里 4 块被请求两次），故按**章**半径裁（锚点章 ±2）。
3. **块高取排版实测值，不心算**：滚屏的块与块要精确无缝拼接，块高必须取渲染引擎实测的行底部（`ReaderTypesetter.measureBlock`，判据抽成可单测的 `fitLines`），不能用「行数 × 行高」——那是拿度量猜几何，每行差零点几像素、25 行累计近 20px。两种方式的正文视口高度不同（滚屏块内没有标题行），故 `pageLineCount` 不同、同一个屏号指向的不是同一段字；切换方式时按**行号**换算落点（旧屏号 × 旧行数 ÷ 新行数），这是全仓唯一一处换算。
4. **滚屏的加载键一律是具体块号，不用「章节首/末页」哨兵**：翻页模式可以拿哨兵当当前页的键（它按该键取状态，哨兵与已解析页键在它那里是一回事），而滚屏按真实块号渲染，哨兵键（-1/-2）永远不会被读到——那样首屏会停在加载态等到天荒地老。故块数未知时先加载第 0 块探出整章块数，落定后再把哨兵解析成具体块号并补发该块的加载。
5. **滚屏列表跨章连续，章段惰性物化，章界只留一个标题项**：进入某章即物化它的相邻两章（探该章第 0 块，加载器回出的 `pageAll` 即该章块数），于是用户滚到章界时下一章早已在列表里、排版也早已落定，跨章不需要任何「切章」动作。块数未落定的章段占 1 个**占位块**，列表不会因此断开——用户滚过去看到加载态/错误态（错误态带重试），而不是「没有下一章」。章段只增不减（一段两个 int），正文才按章距裁剪（决策 2），故往回滚不必重新排版。

   不这么做的话，章界只能靠「上一章/下一章」链接项承担：那是同一件事的第二个入口，且点击切章要重建列表——`clear` 掉全部已加载页、块数归零重探，用户看到一帧加载态、fling 动量也断在章界上。

   **刻意接受的代价**：物化相邻章就是提前把它们的正文取回来（网络书会多一次提前抓取，冷启动时连上一章也会探一次）。这正是「章界无感」的前提——章界处不该等网络；只读前进方向的用户为上一章白付一次抓取，换来往回滚（重读上一段是最常见的回滚动机）时不必等。

   **锚点存语义值 `(章, 块)`，不存扁平 item 序号**：相邻章由占位块展开成 N 块时，锚点上方的 item 数会变、扁平序号整体平移，存序号就等于一次展开把进度写偏一屏。视觉位置交给 LazyColumn 的**按 key 锚定**：item 带稳定 key 时，在首个可见项之上增删 item，Compose 会在 measure 阶段按 key 找回原锚点项（`LazyListScrollPosition.updateScrollPositionIfTheFirstItemWasMoved`），画面不动，也不需要手写 `scrollToItem(anchor + delta)` 补偿、不存在与绘制抢帧的问题。随之而来两条硬约束：**key 必须全局唯一**（重复 key 会锚到另一项，位置静默跳变），且 key 只由 `(章, 块)` 构成、不含扁平序号（序号会平移，拿它当 key 等于每次展开都换身份）；**单次上方插入不得超过约 100 项**（key→index 映射只索引锚点附近 `[30*(i/30)-100, 30*(i/30)+130)` 这个窗口，超窗即锚定失败且不会自愈）。一章通常 5～30 块，远在窗内；真要支持上百屏的超长章得改成分批插入。

## 权衡

- **块内保留标题与页码以换「零换算」（被拒）**：两种方式的正文视口高度就一致了、切换不必换算。代价是滚屏每屏多出一条约 70dp 的空带，且每屏重复一遍章节标题——滚屏的意义正是让标题滚走、让正文连续占满视口。
- **一次性排版整本书、把全书铺成一个列表（被拒）**：item 总数一开始就确定，没有任何惰性展开，也就不需要按 key 锚定。但排版整本书的开销与「按章惰性加载」的取向相反（网络书还得先把全书正文抓回来），且目录会在阅读期间变长（换源、补章），全书 item 数并非真的恒定。惰性物化 ±1 章拿到同样的连续体验，代价只是章段展开时依赖平台的按 key 锚定（决策 5）。
- **自绘虚拟化容器（被拒）**：块高统一（每块恰一屏），自己按绝对像素偏移摆放可见块，锚点补偿就成了自己手里的一次加减法，完全不依赖平台行为。代价是把 LazyColumn 的惰性组合、惯性与 fling、预取全部重写一遍，只为换掉一条平台已经保证的性质。
- **给滚屏单写一套取文/分块（被拒）**：看似让两端各自简单，实为同一份正文两套判定——见决策 2，这正是历史上「上下页接不上」的成因。

## 落地状态

- 2026-09-13 首版落地为「单章块列表 + 章首/章末各一条相邻章链接项」，当时把跨章无缝列为被拒方案，理由是「item 总数要先排版完整本书才知道」与「前插一章会让 item 索引与滚动位置整体平移」。同日按用户反馈（章界不无缝、链接项多余）改为跨章连续列表，即决策 5：前一条前提被「惰性物化 ±1 章」消解，后一条被 Compose 1.11 的按 key 锚定消解（当时未核实平台已有此行为）。链接项与其两条字符串（`prev_chapter_format` / `next_chapter_format`）随之删除；保留集裁剪也从「只有翻页一端做」改成两端都做、单位不同（决策 2）。
