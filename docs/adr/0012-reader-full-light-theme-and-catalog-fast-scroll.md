# 阅读界面分两层配色：正文豁免深浅色、控制器跟随全局主题，保留目录快速滚动条

阅读器迁移到 Compose 后，需对"阅读界面豁免系统深色模式"作范围收口，同时决定是否保留原章节目录快速滚动条。当时的收口是**整片豁免**（正文用阅读背景主题，chrome 层固定浅色），2026-09-13 收窄为**两层口径**：豁免只属于正文层——四档纸张色由用户主动选择，深浅色切换不得改它；chrome 层（顶/底栏、章节目录、亮度/字体/设置面板、弹窗）撤销自建主题作用域，直接继承全局主题，随外观主题模式走浅色或深色。快速滚动条的 Compose 移植决定不变。

## 背景

迁移一度只豁免正文、chrome 层沿用 `MaterialTheme.colorScheme`，系统深色开启时菜单区深色、正文仍为读书主题浅色，偏离原实现且与整体豁免措辞不一致；代码评审据此提出，grill 会话把范围收为整片豁免。

**2026-09-13 再收口**：整片豁免落地后，暗环境里「暗正文 + 纯白控制器」的落差被实机反馈为刺眼。回看当初支撑整片豁免的两条理由，都不成立：

- **「对齐原实现的全白菜单」**——原 View 版 `ll_menu_top` / `ll_menu_bottom` 是硬编码 `#ffffff`，那是深色适配尚未存在时的写法，不是设计意图；迁移 1:1 移植时把缺陷连同交互一起保住了。
- **「让豁免的措辞与作用域一致（整片，而非只正文）」**——「阅读界面豁免系统深色」这条约束真正的归属只是正文那张纸。把豁免扩到整页，等于让一个操作界面去替阅读载体决定自己的明暗。

## 决策

1. **正文层豁免深浅色，控制器层跟随全局主题**（2026-09-13 修订，替代原「整片豁免系统深色」）：

   - **正文**用阅读背景主题（`ReadBookControl` 四档纸张色），深浅色切换不碰它——纸张由读者主动选择，与应用配色是两套事实（术语口径见 CONTEXT.md）。页面内的加载/错误态也画在纸上，同属这一层。
   - **控制器（chrome 层）不再自建主题作用域**：`ReadBookActivity.PageContent` 直接组合页面，继承基类 `AppTheme` 装配点那份 `colorScheme`，于是顶/底栏、目录抽屉、亮度/字体/设置面板、换源与下载弹层、加架确认框随外观主题模式同步走浅色或深色。阅读器因此不再是"子类不得在 `PageContent` 里重复包裹 `MaterialTheme`"那条约定的被点名例外。
   - 判据落在**层**上而不是**页**上：同一页里"读的那张纸"与"操作这张纸的面板"本就属于两套配色事实，强行让它们同明暗才是需要解释的事。

2. **保留目录快速滚动条**：原 `RecyclerViewBar` 移植为 Compose `ReaderFastScroll`——右侧可拖手柄按 y 比例 `scrollToItem` 定位长目录，拖动与列表滚动都显示并各自重启 1 秒无操作隐藏倒计时（fling 期间同样可见）。上千章节的目录纯 fling 翻找效率低，放弃等于可视功能降级。

## 被拒方案

- **仅正文体豁免、菜单/面板跟随系统深色**：~~已拒~~ —— **2026-09-13 翻案并成为决策 1**。当初拒它靠的两条（偏离原实现全白菜单、同一条豁免出现两种口径）现均已失效：前者是把硬编码 `#ffffff` 的缺陷当契约，后者搞错了口径的归属——分裂本来就该发生在"纸"与"操作面板"这两层之间，而不是硬要抹平。
- **控制器跟随所选纸张色**（四档各配一份 chrome 调板）：控制器是操作面，不是纸；四档纸张会让同一套菜单长出四种颜色，明暗判据也从"用户选的开关"退化成"从色值推导"，与外观主题模式重复一套事实源。2026-09-13 明确排除。
- **只把纯白换成中性灰、仍不随深浅色**：治的是"白得太亮"，没治"暗环境里刺眼"——深色环境下仍是一块亮斑，且又多一份只有阅读器持有的调板事实。
- **目录快速滑块接受降级**（`LazyColumn` fling 可满足）：上千章节的目录纯 fling 翻找效率低，属可视功能降级。
- **快照菜单跟随系统深色并改写规格文档**：为免改动而放宽规格承诺，不可取。

## 下游影响

- 正文配色仍由 `ReadBookControl` 阅读背景主题独立控制，chrome 层的深浅色与之互不相干。
- **状态栏图标的判据从「一律按纸张色」改成「压在它下面的那一层」**：顶栏与目录抽屉都把背景延伸到状态栏后面（避让 padding 写在底色内层），可见时图标要跟 chrome 的 `surfaceContainer` 取亮度，收起后才回落到纸张色。沿用旧判据的后果是深色控制器 + 素白纸张时，深色图标被画在深色栏上、状态栏读不出东西。
- **AGENTS.md 撤销「阅读器是子类不得重复包裹 `MaterialTheme` 的唯一例外」**：阅读器已无自建主题作用域，全仓 `PageContent` 一律不包 `MaterialTheme`，无例外。主题装配只有基类经 `lib_common` 的 `AppTheme` 提供这一处。
- 字体面板的阅读主题色卡：未选中描边不再取"主题自身正文色 + 低透明度"（那是按浅色面板画的，深色面板上夜间色卡会整块融进背景），改取当前调板的 `outlineVariant`；预览字仍取主题自身前景色，因为它画在纸上。
- `module_book` 新增 `ReaderChromeThemeRenderTest`：把 `surfaceContainer` 换成探针色，Robolectric 真渲染数像素，锁住顶栏与底栏两条都随调板翻转（写回常量只会让像素变白，布局与语义全绿，故必须数像素）。

## 范围与连带约束

豁免与快速滚动条这两条决定带出若干阅读器特有的形态，各自都有真实取舍，改动前先看清理由：

- **目录载体是全高左侧滑入抽屉（`ChapterListDrawer`），不是底部弹层**：上千条目的目录在半屏 `ModalBottomSheet` 里浏览体验差，全高侧栏才容得下快速滚动条与长章名；它是自绘覆盖层，返回键处置统一收在 `ReadBookScreen` 的 BackHandler。
- **阅读器关掉基类的 insets 处理**（`enableFitsSystemWindows() = false`）：正文背景要一直铺到系统栏底下，因此顶/底栏与目录抽屉自行避让系统栏，且避让 padding 写在 `background` 的内层——写反了就会背景不延伸或内容被系统栏遮挡。
- **每次进入阅读器都重新应用已持久化的手动亮度**（`applyReaderBrightness`）：窗口亮度不跨 Activity 生命周期，不重应用就是"设置里存着 30%，进阅读器又变回满亮"。
- **顶栏返回箭头与硬件返回键语义不同**：箭头 = 退出阅读器（未加入书架时先弹确认），硬件返回键 = 走 BackHandler 处置链（菜单可见时先收菜单）。两者曾共用同一路径，结果是箭头被"关菜单"分支吃掉，只隐藏控制界面不退出。
- **章节/亮度滑条是自绘 `ReaderSlider`，不用 Material3 `Slider`**：M3 新版滑条的竖条手柄在这两条紧凑行里过重、与同行文字图标抢视线，且取值停在最小端时轨道另一端会露出端点圆点，读起来像控件坏了。手势语义与替换前一致（按下即定位、拖动实时回调、抬手取整跳章）；触点→数值映射固定以静止态旋钮尺寸为基准，否则按下放大瞬间数值会抖。
- **字号档位走点选胶囊，不走滑条**：每次改字号都要重排全文分页，拖动产生的连续回调代价不可接受。阅读背景主题的色卡需要展示主题名，故 `ReadBookControl.TextDrawable` 携带 `labelRes`——配色值本身表达不了"这是哪一档"。
