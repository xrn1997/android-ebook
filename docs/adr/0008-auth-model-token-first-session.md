# 认证模型：邮箱为登录主标识，会话恢复走 token 优先、密码不落盘

项目无短信通道，旧实现依赖密码落盘重放恢复会话，存在明文泄露面且无真实续期能力。决定采用「邮箱为登录主标识 + 用户名仅作展示标识（可重复、可后改）」的账号体系并弃用手机号语义，密码不落盘，启动会话恢复由密码重放改为 token 优先，配套 access（JWT 2h）+ refresh（30 天，服务端存哈希、刷新时轮换）双 token 机制；密码变更分两路——已登录走旧密码校验，未登录走邮件验证码重置。

## 动机

- 项目无短信通道，"11 位手机号"标识是假语义：暗示用户会收到验证码（实际收不到），且无法承担找回密码通道职责；邮箱必填使找回链路闭环（SMTP 授权码免费）。
- 密码落盘（两处 SharedPreferences）的唯一用途是启动时重放密码重新登录——旧服务端无 token 会话概念的遗产。新后端有 JWT，密码重放可以整体删除，消除明文密码在 root/备份/抓包场景的泄露面。
- 单用户量的个人项目，双 token 的完整静默续期实现成本可控（服务端一张表 + 一个端点），用户体验收益大（30 天内打开过 App 即无感续期），是"登录过期→跳登录页"体验的根治手段而非补丁。

## 权衡

- **弃手机号而非"手机号+密码但不做短信"**：放弃与国内主流形态的对齐，换取语义真实；登录页文案/校验全部去手机号化。
- **注册不做「先建号再激活」的邮件往返**：不发激活链接、不允许未验证邮箱先用着；验证码是唯一的邮箱所有权证明手段，注册与找回密码各调一次、一律由服务端校验（客户端不留本地假码）。这样既闭环了找回链路，又不必维护「已注册但未验证」这一中间态。
- **refresh 只做轮换、不做重放检测**（发现旧 refresh 被重放则吊销该用户全部会话）：简化版对个人项目足够，检测逻辑后续可低成本补上。
- **token 过期不做逐调用点分支**：会话"救不回来"（refresh 也失败）时经 SharedFlow 事件统一收口（清会话+跳转登录页），调用点零感知；逐调用点处理必然遗漏且行为不一致。
- **头像/昵称不在认证链路里做**：用户表加字段、登录响应如实返回即可，认证迭代只补数据通道。上传能力是独立接缝（先上传拿 URL、再由更新资料端点提交该 URL），不掺进 token/会话机制——否则「会话恢复」这条链路的验收边界会被资料编辑稀释。

## 下游影响

- `ebook-server`：响应信封改 `{code, error, data}` + 五位业务码，HTTP 恒 200；用户表加 email/nickname/avatar；新增改密、发码/验码（含 SMTP）、刷新、登出端点；refresh_tokens 表。
- `android-ebook`：`UserSessionManager.saveSession` 去掉 password 参数（改收 refresh token），`getPassword()` 删除；`SplashActivity.autoLogin` 从密码重放改为会话直恢复；`lib_ebook_api` 增加静默刷新（单飞互斥 + 一次重放）与会话过期事件；`module_login` 校验与文案去手机号化、验证/改密页改造为邮箱语义；基址改由 `local.properties` 注入 BuildConfig。
- `module_me`：设置页新增"修改密码"入口（已登录改密路径）。
