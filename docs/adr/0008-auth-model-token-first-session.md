# 认证模型：用户名+邮箱账号体系，会话恢复走双 token、密码不落盘

登录模块现代化（范围档 B）的认证模型决策：账号标识为**用户名**（登录主标识）+ **邮箱**
（注册必填，密码找回唯一通道），**弃用手机号语义**；**密码不持久化**，启动会话恢复由
"重放密码自动登录"改为 **token 优先**，并配套 **access（JWT 2h）+ refresh（30 天，服务端
存哈希、刷新时轮换）** 双 token 机制；密码变更分两路——已登录走旧密码校验，未登录走邮件
验证码重置。

## 动机

- 项目无短信通道，"11 位手机号"标识是假语义：暗示用户会收到验证码（实际收不到），
  且无法承担找回密码通道职责；邮箱必填使找回链路闭环（SMTP 授权码免费）。
- 密码落盘（两处 SharedPreferences）的唯一用途是启动时重放密码重新登录——旧服务端无
  token 会话概念的遗产。新后端有 JWT，密码重放可以整体删除，消除明文密码在
  root/备份/抓包场景的泄露面。
- 单用户量的个人项目，双 token 的完整静默续期实现成本可控（服务端一张表 + 一个端点），
  用户体验收益大（30 天内打开过 App 即无感续期），且是"登录过期→跳登录页"体验的
  根治手段而非补丁。

## 权衡

- **弃手机号而非"手机号+密码但不做短信"**：放弃与国内主流形态的对齐，换取语义真实；
  登录页文案/校验全部去手机号化。
- **注册时不做邮箱验证**：验证码只在找回密码时动用；个人项目无防滥用需求，注册摩擦最小化。
- **refresh 只做轮换、不做重放检测**（发现旧 refresh 被重放则吊销该用户全部会话）：
  简化版对个人项目足够，检测逻辑后续可低成本补上。
- **token 过期不做逐调用点分支**：会话"救不回来"（refresh 也失败）时经 SharedFlow 事件
  统一收口（清会话+跳转登录页），延续 ADR-0004 的事件模式；调用点零感知。
- **头像/昵称本期只补数据通道不做上传**：server 用户表加字段、登录响应如实返回，
  上传端点留独立迭代，不稀释认证链路的验收边界。

## 下游影响

- `ebook-server`：信封改 RespDTO 契约（见 ADR-0007）；用户表加 email/nickname/avatar；
  新增改密、发码/验码（含 SMTP）、刷新、登出端点；refresh_tokens 表。
- `android-ebook`：`UserSessionManager.saveSession` 去掉 password 参数（改收 refresh
  token），`getPassword()` 删除；`SplashActivity.autoLogin` 从密码重放改为会话直恢复；
  `lib_ebook_api` 增加静默刷新（单飞互斥 + 一次重放）与会话过期事件；
  `module_login` 校验与文案去手机号化、验证/改密页改造为邮箱语义；
  基址改由 `local.properties` 注入 BuildConfig。
- `module_me`：设置页新增"修改密码"入口（已登录改密路径）。
