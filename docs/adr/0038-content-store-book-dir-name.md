# 内容仓库的书目录名由 BookStore 从 note_url 派生，网络书取 md5

书目录名此前直接取 `book_shelf.note_url`，而网络书的 note_url 是站点 URL——含路径分隔符，于是落盘成了 `books/https:/host/30/cNNNNN.txt` 这样的嵌套目录树，所有按「`books/` 第一层目录名 = 一本书」工作的逻辑全部判错：启动对账把**全部网络书的章缓存**当无主目录删光（2026-09-13 设备实测：重启前 2 个章文件、重启后 0 个，冷启动重读早已缓存的章仍走网络重抓），缓存管理页把所有网络书数成 1 册，删一本 URL 路径互为前缀的书会连带删掉另一本。决定把目录名收口成 `BookStore.dirName(bookId)` 一处派生：bookId 本身已是合法单段名就原样用，否则取 md5。

## 决策

1. **派生只在 BookStore 内做一次，调用方一律传 bookId**：`chapterRef` / `bookDir` / `beginImport` / `commitImport` / `reconcile` / `cacheMarker` 全部经它，调用方不得自己拼目录名。理由是读写两侧各拼一次就会漂移成「写完永远读不到」——这类错位不报错也不闪退，只表现为缓存永远命不中（`cacheMarker` 尤其隐蔽：拿 note_url 原值拼片段，对网络书的「删书/强刷后失效正文缓存」全部空转）。
2. **已是合法单段名的 bookId 原样用，不对所有 bookId 统一取 md5**：本地书的 note_url 就是内容 md5，原样用即恒等映射，于是 `chapter_list.content_ref`（本地书存完整相对路径、且该列是自然键）的既有取值一字不变，不需要 DB 迁移。统一取 md5 看着更整齐，代价是既有行全部指向不存在的文件，还要处理导入补章按 `content_ref` 判重、新章索引取 `max+1` 时的新旧形状混用。
3. **非法字符判据含 Windows 保留字符（`/ \ : * ? " < > |`），不只路径分隔符**：Android 上只有 `/` 与 NUL 非法，但判据必须与宿主无关——同一个 note_url 在设备与开发机单测里要派生出同一个目录名，否则单测绿的形态与真机跑的形态不是一回事（实测：`https:` 在 Windows 上根本不是合法目录名，`mkdirs` 静默失败后写文件抛 `FileNotFoundException`，红的是主机差异而不是缺陷本身）。

## 权衡

- **改成让对账认嵌套布局（被拒）**：`reconcile` 递归下探、按 note_url 归一化出的相对路径比对。改动面更小、目录名保持可读，但只修三处症状里的一处——册数统计与连带删除照旧错；而且「第一层目录 = 一本书」这条不变式就此永久不成立，此后任何按目录遍历的功能（按书清理、占用统计、导出）都要重新处理嵌套，目录深度还由站点 URL 路径决定、不可控。修不变式比让每个消费者绕开它便宜。
- **用 md5 而不是把非法字符替换掉（被拒）**：替换能保住可读性，但会撞——`https://x/a/b` 与 `https://x/a_b` 替换后同名，两本书共用一个目录就是串书。md5 与仓内 `LibraryDiskCache` 对 sourceUrl 取 md5 当文件名的做法同构，代价只是排查时先算一次 md5。
- **现存网络书缓存目录不迁移**：旧的 `books/https:/…` 在新规则下成为孤儿，由下一次启动对账回收。不写迁移是因为它没有可保住的收益——那份缓存在旧规则下每次启动都被删光，用户手里本来就不存在「已积累的缓存」。本地书目录名逐字未变，不受影响。
