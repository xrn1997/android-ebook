# ADR 规范

> 以 domain-modeling 技能的 ADR-FORMAT.md 为底、按本仓既有 ADR 的实际复杂度校准；与 AGENTS.md 约定冲突时，以 AGENTS.md 为准。

## 文件与编号

- 放在 `docs/adr/`，命名 `NNNN-slug.md`（顺序编号 + 短横线小写 slug）
- 编号：扫现有最大号 +1，不复用、不跳号

## 什么时候写 ADR

三条判据同时成立才写：

1. **难以回退**：事后改变主意的代价足够大
2. **无上下文会令人惊讶**：未来的读者看代码会问「为什么当初要这么做？」
3. **真实权衡的产物**：确实存在别的可选方案，而你基于具体理由选了这一个

容易回退的不写（反正你会改它）；不令人惊讶的不写（没人会问为什么）；没有真实替代方案的不写（除了「做了显而易见的事」无甚可记）。

够格的典型：

- **架构形状**：「写模型事件溯源，读模型投影进 Postgres」
- **上下文间的集成模式**：「Ordering 与 Billing 走领域事件，不走同步 HTTP」
- **带锁定的技术选型**：数据库、消息总线、认证服务商——只算换掉要一个季度的
- **边界与归属**：「Customer 数据归 Customer 上下文，其他上下文只凭 ID 引用」——显式的「不做」同样有价值
- **刻意偏离常规路径**：「手写 SQL 而不用 ORM，因为 X」——拦住下一个人去「修好」刻意为之的事
- **代码里看不见的约束**：「合作方契约要求响应 <200ms」
- **非显而易见的被拒方案**：考虑过 GraphQL 选了 REST 且理由微妙——不记，半年后还会被重提

## 篇幅跟着决策重量走

### 每篇必有（轻决策到此为止）

```md
# {决策式标题：读完标题即知结论，如「X：从 A 到 B」「把 Y 收口在 Z」}

{导语 1~3 句：背景一句 + 决定一句 + 理由半句；评审来源与日期可在此带过。}
```

只有标题 + 导语也是合格 ADR——价值在记录「决定了什么、为什么」，不在填满章节。

### 常用四件套（决策重一分，多加一件）

| 章节 | 什么时候加 |
| --- | --- |
| `## 动机` / `## 背景` | 「为什么」一句话装不下时：多股作用力、要澄清的误报、历史包袱。讲「为什么要变」用动机，讲「现状与问题」用背景，二选一 |
| `## 决策` | 决定多于一件互相牵连的事，或单条决定需要分条展开约束。编号条目，每条自带理由 |
| `## 权衡` | 存在被放弃的方案、且「为什么不」需要交代时。同样逐条给理由 |
| `## 下游影响` | 改动横跨多模块/多文件，读者需要知道波及面（改了哪些类、清单、资源、测试） |

### 例外件（体系性决策才需要）

- `## 被拒方案`：拒绝本身需要论证、不记会被重提时
- `## 落地状态`：实现偏离决策、或决策是尚未实现的规划稿时。带日期的就地补记，只记事实与偏差（如「正文中的某类已不存在」），不挂人工验证清单
- `## 遗留`：刻意不做的部分与重启的触发条件
- 专项自定章节：决策本身是一套体系时按需命名（如「Schema 演进」「判据」「保留项」）

## 写作纪律

- 编号条目（决策/权衡）每条自带理由，禁止只有结论没有 why
- 章节名允许近义（动机/背景、权衡/后果），同一篇内保持一致
- 硬规则在 AGENTS.md，此处不重复：正文不交叉引用其他 ADR、跨仓编号禁引、代码与文档同步、就地更新或整篇重写（不层层打补丁）
