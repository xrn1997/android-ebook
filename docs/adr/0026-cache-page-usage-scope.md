# 缓存管理页的占用口径：应用缓存可清、书籍内容单列且不删，测量归内容仓库自己

2026-09-06 架构评审（`module_me` 逐模块迭代）定下三件事：**「缓存」在本页只指 `cacheDir`**；
书籍内容（`filesDir/books/<bookId>/cNNNNN.txt` 的章文件）**单列一行呈现**：
它不计入可清理总量、本页也不提供删除入口（只把那行点成「去书架管理」）；**「书籍占了多少、有几本」由内容仓库 `BookStore.storageUsage()` 一次遍历回答**，
调用方不再遍历别人的目录。递归求和收成一个 `File.treeSize()`（`lib_book_common`），
缓存与内容仓库共用——同一条「占用」不该有两份算法。

## 背景

缓存管理页原先只统计 `cacheDir`，而这台设备上真正的大头往往是藏书：一本 2000 章的书
约 6 MB，几本书就能压过整个缓存。用户看到的「缓存总占用 12 MB」与系统报告的
「应用占用几百 MB」差一个量级，页面对此毫不解释。可选方向曾经摆过四个：
就地可删（在缓存页删书）、新开一个「存储」页、只改文案、以及只读呈现。
选前者会在书架长按删除之外造出**第二个删书入口**（两处口径迟早不一致）；
选后者在当下只有「缓存 + 书籍」两个租户，为一个数字新开一页是过度设计。

同时有一条必须先确认的事实：页面的文案**本来就是自限的**——标题「缓存总占用」、
清理确认逐项列出「图片缓存、临时文件及其他缓存」。所以这不是「页面上写着假话」，
而是「少给了一個用户真正想知道的数字」，修法因此是补信息，不是改措辞。

## 决策

1. **这一行不参与清理，但可点——点到书架去管理**。不用列表项组件 `CommonListItem`：它把 `onClick` 定为
   必传，而这里存在「书架路由取不到 → 只展示不可点」的形态（独立运行时 `module_main` 不在依赖图里），
   硬套就会留下一个点了没反应的假入口。故按本页明细行的同款手写 `Row`，配色取
   `surfaceVariant`/`onSurfaceVariant` 中性语义色，仅在可点时补一个右向箭头作可供性提示。
2. **不计入可清理总量**。`CacheUiState` 两组字段分开：`totalText`/`totalBytes` 只含 `cacheDir`
   （驱动「清理全部」按钮的可用态与确认弹窗），书籍侧是 `booksSizeText` + `bookCount` 单独一栏。
   混在一起会让用户以为一键清理能删掉藏书，也会让按钮因为「反正有数字」而常年可点。
3. **测量归所有者，且每个统计只走一遍树**。`BookStore.storageUsage()` 一次遍历同时给出
   `bytes`（全部章文件，含 `.tmp` 与散落文件——它们确实占磁盘）与 `bookCount`（只数书目目录，
   半成品不算一本，否则缓存页会报出书架上不存在的册数）；`CacheManageViewModel` 注入 `BookStore`
   只取这一个结果，不碰目录形状。分两个方法本来也能跑，但缓存页每次刷新都要这两个数，
   分开就是**把整棵章文件树走两遍**——几十本书 × 数千章文件时是能感知的 IO，故合并。
   同一轮里缓存侧也改成一次分档遍历（原来是「总量减图片与临时」的差值法，图片目录被走两遍，
   还要为并发写下的负差值钳位；分档累加后总量恒等于三档之和，少一趟遍历也没有负数可言）。
   递归求和本身是域无关件，收在 `com.ebook.common.util.treeSize`（与 `DateUtil` 同批，
   真正的家是外部库 `lib_common`，等联动窗口上移）。
4. **页面职责边界写进代码**：`CacheManageViewModel` 的类 KDoc 与页面注释都要说明
   「书籍内容不是缓存，本页不删它」，避免下一个人顺手把它并进清理逻辑。

## 权衡

- **跳转用现成的路由，不新增跨模块约定**（原写「刻意不跳转」的理由经核实不成立，已按实测更正）：
  曾判断「要主页的 Tab 选择契约 + 独立宿主挂路由占位」。查 `module_main` 后是另一回事——
  `MainActivity` 既没声明 `launchMode` 也不处理 intent extra，而它的 `startDestination` 就是书架，
  所以 `FLAG_ACTIVITY_CLEAR_TOP` 会重建它并落回书架，不需要任何「选哪个 Tab」的新约定。
  代价是本页与设置页一并出栈：从「去管理我的书」的语义看可接受。
  独立运行时该路由确实不存在（TheRouter 找不到只记一行日志），因此先 `matchRouteMap` 探测，
  取不到就把这一行退化为纯展示 + 指向书架的说明文案，而不是挂一个假箭头。
- **不提供删除**同上：删书的既有唯一入口是书架长按，且它连着内容仓库与书架记录的对账，
  在设置页另开一处只做一半（或做全套）都不划算。
- **这一行不用共享列表项组件**是取舍而非疏漏：为「可选 onClick」去扩一个全仓共用的
  组件接口，等于为一个调用点摊薄所有人，比在本页手写 30 行更浅。

## 下游影响

- `lib_book_common`：新增 `File.treeSize()` 与 `BookStore.storageUsage()`（返回 `StorageUsage(bytes, bookCount)`）；
  `CacheModel` 删掉私有的递归求和改用 `treeSize`，且 `cacheBreakdown` 改为一次分档遍历——「占用」从此一份算法、一遍树。
  由 `TreeSizeTest`（3 例，纯 JVM 临时目录）与 `BookStoreTest` 新增 3 例（一次遍历给出字节与册数、
  空仓库归零、目录不存在不抛）锁住。
- `module_me`：`CacheManageViewModel` 多注入 `BookStore`，`CacheUiState` 多 `booksSizeText` 与 `bookCount`；
  页面多一张「书籍内容」卡，值显示为「占用 · N 本」，文案四条（标题 / 值格式 / 可点版说明 / 无路由版说明）。
  由 `CacheManageViewModelTest`（3 例，Robolectric + 双临时目录）锁住：书籍数字单独呈现、
  不进可清理总量、`clearAll()` 后书籍文件字节数不变、空仓库显示 `0 B` 而不是空占位。
  测试等真实 IO 线程用 `awaitUntil` 轮询，不靠固定 sleep——`CacheModel`/`BookStore` 的遍历
  跑在 `Dispatchers.IO` 上，不受虚拟时钟控制。跳转在 Activity 侧（探测 + `CLEAR_TOP`），
  属视图层无 JVM 覆盖，只能靠下面的装机项。
- 人工验证项（Agent 止于构建）：装机后打开「我的 → 设置 → 清除缓存」，期望看到「书籍内容」一行
  给出与藏书量级相符的数字、且「缓存总占用」仍是原来的小数字；点「清理全部缓存」后期望
  缓存归零而书籍行数字不变、回书架书还在；点该行期望带右箭头并直接落回书架（设置与缓存两页一并出栈），
  独立运行时该行应无箭头、不可点。
