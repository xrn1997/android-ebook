# 不可信 JS 执行：零权限隔离进程 + 自集成 QuickJS

书源规则要能内嵌陌生 JavaScript（脚本书源的前提能力），而这些代码来自社区、完全不可信。2026-09-08 的 grill 设计会话裁决：执行器采用「独立 Android 进程（`isolatedProcess` 零权限）+ 引擎源码自集成（QuickJS C，自有 C++ 桥接层）+ 最小白名单 Host API + Binder 双向协议」，deny-by-default，多层防御不依赖单一边界。

执行器已于 2026-09-09 按本文落地。

## 背景

- 内嵌 JS 是书源生态的常态（642 条实测语料中 62% 含脚本代码，且常是整段内容提取逻辑而非胶水），不执行 JS 就只能覆盖少数声明式源。
- 引擎内核本身不是安全边界：QuickJS 这类 C 引擎存在内存安全型漏洞的可能，脚本一旦配合漏洞逃逸，获得的是「所在进程」的能力——在主进程内执行等于把远程代码放进业务进程。
- 资源耗尽是低成本攻击：死循环、指数内存分配、无限递归都不需要任何漏洞。
- 本仓此前的安全姿态（书源请求走纯净客户端、第三方永不接触用户 token）建立在「主进程不执行陌生代码」之上，此决策不能破坏它。

## 决策

1. **引擎选 QuickJS，以源码直接集成进自有 C++ 执行器**。QuickJS（C、MIT、原版内核久经考验）体积小、启动开销低、C 集成简单。桥接层（runtime 管理、绑定注册、限值控制）完全自有、可审计——这是全仓安全关键路径，不引入第三方绑定层。
2. **执行器进程声明 `android:isolatedProcess="true"`，零权限是内核强制的**。普通独立进程与主进程同 uid、同权限集，「禁止网络/文件」就只剩绑定层约定，原生层漏洞可直接绕过开 socket；isolated 进程运行在独立 uid 与受限 SELinux 域下，无 socket、无文件、无 App 数据，deny-by-default 从约定升级为操作系统强制（该机制自 API 16 存在、Android 8 起经 WebView 沙箱渲染进程大规模验证）。同一份声明里 `exported="false"` 是配套的：控制面那对方法没有任何鉴权，只有本应用自己绑得到才不至于变成整机入口。
   - **属性写了还要自己验**：「这个进程真的被隔离了吗」唯一的保证来自清单上那一个属性，而它一旦被改掉（例如退路落地成 `android:process` 却没回头删掉 `isolatedProcess`），执行器就带着「脚本能读私有目录」跑起来——功能一切正常、边界整片没了。故 `SandboxService.onBind` 先过同一道判据，不隔离就返回 null 并记一条 error：主进程拿不到 binder，最终归成一次连接超时。**宁可报「沙箱不可用」，也不在不设防的进程里跑别人的脚本。**
   - 判据是 `Build.VERSION.SDK_INT >= P && Process.isIsolated()`，短路次序是刻意的：`Process.isIsolated()` API 28 才有，写反等于在 26/27 的设备上第一次调用即崩；`SDK_INT` 是静态字段，在 JVM 单测里读作 0，于是整条判据在单测里恒为 false，不会去碰 mockable jar 里那些「Method … not mocked」的桩。**副作用**：minSdk 26 与 27 的设备上判据恒为 false，执行器按上一条自我拒绝，含 JS 的规则段在那批设备上跑不起来（声明式脚本文源不受影响）。这是 fail-closed 的已知边界，不是漏改。
   - 拿「是不是隔离的」而不是「进程名是不是 `:js`」做判据：进程名由系统生成、随版本变，而要问的正是「这个进程有没有被削减能力」；判错的代价也不对称——按名字比对若在主进程误判，产出的是「整个 App 起来但没初始化」。
   - 自有 `.so` 在个别机型加载异常时的现状是回 `UNAVAILABLE`（该源本轮按失败处置，主进程不受累）；真要退化成普通 `:js` 进程，那是回本文重开一条决策——先改这里、再去掉 `isolatedProcess` 与上面的自检，协议与缝隙不变，只是边界强度降级。
3. **能力模型 deny-by-default**：脚本只见 ECMAScript 标准能力加显式注册的白名单 Host API；文件、网络、反射、JNI、Java/Android 大 API 面一律不存在，而非存在后禁用。
   - **内建的阻塞原语也要在运行时关掉**：vendored 内核里 `Atomics.wait` 的等待队列用 `pthread_*`（约 15 处），它属语言内建对象、去掉等于改内核，所以随包存在，靠 `JS_SetCanBlock(rt, 0)` 让它直接失败——执行器线程上做不起「等别人唤醒」。
   - 随包源码里另两处已当场核过，用来确认「零能力面」不是想当然：`quickjs-libc.c`（POSIX/`os.*`/worker/信号处理层）**压根没进包**，脚本自然看不到这些能力；`dtoa.c` 的 `#include <setjmp.h>` 是上游的死 include，全文没有一处 `setjmp`/`longjmp`/`jmp_buf`，故内核的超时与栈溢出都不走 `setjmp` 长跳（超时走 `JS_SetInterruptHandler`，深递归走 `JS_SetMaxStackSize` 的内核栈检查）。
4. **执行协议 `execute(模式, 脚本, 绑定) → (status, result, error)`，Binder + JSON 控制面**；超时不给「时长」参数，由主进程把**绝对期限**（单调时钟毫秒）算好随帧带过去——挂钟预算只有一个起点，执行器不必猜主进程已经等了多久。并扩展**双向回调通道**：脚本执行中可回调主进程完成两类事——递归规则求值（脚本调用解释器解析规则）与网络受限代理。回调实现一律由主进程以受限方式提供。递归求值的嵌套层**不再执行 JS**：一帧之内再入一帧会让按帧记账的超时与堆限失去含义（打不断一棵还在跑的子树）。嵌套拿到的是关掉 JS 的上下文视图，故其中的 JS 段抛出的仍是「需脚本沙箱执行器」那句类型化异常——读起来像「本机还没装」而真话是这一层刻意不给；不另造一套话术，是因为判据本来就只有一处（递进嵌套层的上下文关没关 JS），多一个入口只会多一处会漏判的地方。变量表跨嵌套按引用共享，页面基准按快照传递。
   - **只绑不启**：隔离服务不支持 `startService`，进程只能由 `bindService` + `BIND_AUTO_CREATE` 拉起。每次 `open()` 是一次独立的绑定、解绑挂在返回通道的 `close()` 上，**不把 ServiceConnection 存在连接器字段里**——重连时旧的 Connection 必须与旧通道一起作废，否则旧 binder 的解绑会顺手掐掉新绑定的连接。
   - **连接回调投递在调用方的主线程上**：`bindService` 带 `Executor` 的重载是 API 29 才有，本仓 minSdk 26。这不构成新风险，前提是执行器客户端那条主线程守卫（见决策 6）——绝不会有 execute 停在主线程上等这次回调；代价是主线程长时间占住时连接会等到 `bindTimeoutMs` 超时，症状是一句可命名的「不可用」而不是无声卡住。
   - **连接期限单列一个数**（`bindTimeoutMs`，2 秒），不与规则的挂钟预算混用：绑定失败要尽快报不可用，好让调用方走「这条源今天解不出来」的话术，而不是让一次冷启动的进程创建吃掉整条规则的 5 秒。系统拒绝绑定（服务不存在/被禁用）时不会回调任何一次 `onServiceConnected`，故那条路径必须自己收口。
   - **连不上抛 `SandboxUnavailableException` 而不是通道死亡异常**：客户端对后者会「重连并重放一次」，而一次都没连上的调用没有可重放的副作用，重放只是再等一遍连接期限——把一个 2 秒的坏消息变成 4 秒。
   - **同一时刻只有一帧在飞**，由客户端的 `inFlight` 锁保证（`:js` 侧没有第二道锁，binder 自带至多 15 条线程池线程）。这条不变式是字节限值能留出余量的唯一前提，放开那把锁，字节上限就要跟着减半。
5. **资源限制四件套**：wall-clock 超时（经内核中断器打断）、堆上限、JS 栈上限、请求/响应大小上限。超限销毁 runtime；无法安全恢复则杀进程，主进程经断连感知后自动重启。runtime 按任务复用、任务边界强制重置——脚本之间不共享任何状态（防 globalThis 污染）。任务边界取「一次沙箱调用」而非「一次解析任务」：每次 `execute` 前重建 `JSContext`（`JSRuntime` 仍复用，重建的是全局量与闭包所在的那一层），脚本经 `globalThis` 留下的东西活不过一帧。代价是跨段的全局缓存写法失效，换来的是「一段污染毒到整本书」不可达——污染没有可观测信号，只能靠边界粒度消掉。
   **下面两道限值的语义由设备实测补定**：
   - **JS 栈上限是天花板，不是实际值**。内核判的是「距栈顶已用多少字节」，而一条线程实际有多少栈由**跑它的是谁**决定（应用内新建的 Java 线程约 512 KB，binder 线程与主线程各是另一档）。预算大于剩余栈时，深递归先把 native 栈撞穿成 SIGSEGV——整个执行器进程没了，内核那句 stack overflow 来不及抛。故每次执行前按**本线程**剩余栈再收一道，配置值只当上限。
   - **「内存超限」不能只按异常文本认**。堆真的到限时，内核要说那句 `out of memory` 得先建出错误对象、再建 message——那一笔分配同样落在限值之外，于是抛出的是裸 `null`，或一个**没有 message** 的对象（内核不检查定义属性的返回值），按文本归类就报成一次普通运行时失败。唯一的直接证据在分配器侧：桥接层自己接管分配（拒过一次分配 + 这条异常说不出独立信息 ⇒ 判为内存超限）。曾试过给被拒之后的小额分配留宽限窗口、让内核把话说完整，实测否掉：到限之后先到来的是脚本自己的越限分配，窗口在它下次越限时就被吃光，而窗口开着的那段时间确确实实越过了配置的限值——只留代价、不留收益。
   - **字节上限的尺子不是内存，是 binder 事务缓冲**：每个进程约 1 MB，且被该进程所有在飞事务共用（请求帧、结果帧、单次 host 回调回来的整页 HTML 各一档、同为 900 KB）。写 8 MB 只会让超限的帧在现场抛 `TransactionTooLargeException`——一个未类型化、且只在真机上出现的失败；判在本地才换得到一句「这页太大」的人话。**每任务外呼次数上限**（40）由主进程侧计数，执行器与守门器都不持计数器；口径来自语料：一轮正文解析通常是「取文 + 若干 CDN 图片 + 一次翻页探测」，聚合搜索里单源单页最多十几次，超出这个量级的脚本几乎必然是 `while(true) ajax()`。**回调重入深度**另有一档（8）：脚本套规则、规则再套脚本，超深即失败，不指望内核的栈限来兜。
6. **Host API 白名单按语料频谱定版**（642 条源统计）：纯计算类注册为 JS 白名单 API（md5、base64 族、对称加解密、hex、时间格式化），实现经 JNI 落**执行器进程内的 Kotlin/JDK**（`MessageDigest`/`Cipher`/`Base64` 撑摘要与加解密，`SimpleDateFormat` 撑时间格式化，hex 是十行手写），仍然零 IPC。原话说的是「做成 C++ 原生 API」，改成 Kotlin 的理由：手写 AES/MD5 的 C 实现约 900 行且在本仓不可测（JVM 测不到 C），换成 JDK 后可用真实向量在 JVM 上锁住；隔离进程本就零权限，两种落点在能力面上等价，安全属性一分未动。JS 侧名字与协议不变，将来 benchmark 认定这是热点时只改分发一侧。网络类一律经主进程受限代理（仅 http(s)、拒绝私网地址、大小/超时/限流上限、按源导出可解析 host 白名单、永不附加凭证）；递归求值与变量存取走回调通道；toast 类映射为日志；浏览器自动化、登录流程、验证码一族不支持；旧时代的 Java 类桥（反射访问 Java 标准库）不支持。代理回调在主进程的 binder 线程池线程上同步返回（`runBlocking` 等 `suspend` transport 的结果，transport 内部切 `Dispatchers.IO`，真正阻塞的是 IO 池线程）。这条链路成立的前提是**永不在主线程调沙箱**——主线程调过去就是等自己，执行器客户端侧有主线程守卫把它挡在抛异常那一步。
7. **主进程永不加载引擎**：不可信代码与引擎内核都只存在于执行器进程——`System.loadLibrary` 只出现在 `QuickJsNative` 这个 `object` 的初始化里，而只有执行器侧的桥接层会触到它；主进程没有任何路径会让它初始化。加载失败也不抛，`loaded=false` 时直接回 `UNAVAILABLE`，一次 `external` 调用都不发（整条链路的要求是「失败是有名字的结果」）。崩溃不传染——解析器侧对该书源本轮请求按失败处置（聚合搜索天然容忍单源失败）。
   - **`Application` 仍会被实例化在执行器进程里**，这是隔离进程的一条框架事实：`ActivityThread.handleBindApplication` 在隔离进程上只跳过 `setupGraphicsSupport`、`TrafficStats.init` 与字体预加载三处，**不跳过 `makeApplicationInner`**。所以进程门必须落在 `BookApplication.onCreate` 与 `MyApplication.onCreate` 的第一句（判据即决策 2 那条 `SandboxProcess.isInIsolatedProcess`），早于主题装配与任何读 SharedPreferences 的初始化——隔离进程读不到本应用的数据目录，留着那些初始化只是一串看不懂的 IO 失败。判据反过来误判主进程更严重（「整个 App 起来但没初始化」），这也是它只该有**一处**实现的原因：判据分属三个模块的多个调用点，把 `SDK_INT` 门槛写四遍就会漏一遍。
8. **构建口径**：本仓首个 C++ 模块，build-logic 新增 NDK/CMake 约定插件 `xrn1997.android.native`；release 仅 `arm64-v8a`，debug 构建附 `x86_64`（模拟器可用）。
   - **ABI 口径是安全语义、不是构建细节**，所以一处生效、一处审查：多余 ABI 等于多份可被研究的内核副本。而 **debug 的 `x86_64` 刻意不写进插件**，由各模块在自己的 `buildTypes["debug"]` 里显式加——放进插件就藏进了一处不会随模块新增而被复查的地方，写在模块里才能让「谁多带了一份内核」在 diff 里当场可见。
   - `ndkVersion` 与 CMake 版本钉死在版本目录：AGP 默认值随小版本漂移，会让「同一份 C++ 在不同人机器上编出不同 `.so`」变成不可复现的问题；升级 NDK 因此是一次显式改动。ABI 集合是策略不是版本，故留在插件里不进目录。
   - 插件必须在 Android 插件之后应用，且用 `error(...)` 硬失败而不是 `findByType(...)?.apply {}`：后者在插件缺席时是静默空转——装配「成功」而 NDK 版本、ABI、CMake 路径一条都没生效，症状要等到打出全 ABI 或用了错误 NDK 才浮现。
   - **`HostDispatcher` 的 Kotlin 入口靠 C++ 侧按类名与方法名字符串解析**（`FindClass` + `GetStaticMethodID("handle", …)`），不是 `native` 方法，故 AGP 默认那份 `-keepclasseswithmembernames class * { native <methods>; }` 覆盖不到它，必须由 `lib_book_source/consumer-rules.pro` 显式 keep——R8 一改名，`FindClass` 在 `nativeCreate` 里就失败并返回 0，Kotlin 侧看到的是一句把原因指向内存配置的「沙箱 runtime 创建失败（堆上限 … 字节）」，runtime 根本建不出来，连不到「每次回调找不到入口」那一步。

## 权衡

- **isolatedProcess vs 普通独立进程**：isolated 带来跨进程调试成本、进程冷启动、以及 .so 加载的机型兼容残余风险（保留退化路径）；换来的是「网络/文件默认拒绝」从代码约定变成内核强制——对一个「执行陌生人代码」的功能，这是主要安全边界名实相符的最低配置。
- **QuickJS vs V8 / Rhino / WebView**：V8 性能强但体积与攻击面大、集成重；Rhino 主流且纯 JVM，但目标生态已弃用其行为档案；WebView 能力过剩且自带浏览器攻击面。QuickJS 在启动开销、体积、集成复杂度与行为对齐之间取平衡；性能不足再评估 V8。
- **每脚本独立 runtime vs 按任务复用**：前者隔离语义最干净但每次执行付 runtime 创建成本；后者在「同一本书解析任务」粒度保持隔离（任务边界重置），执行频度高的解析路径成本可控——按 benchmark 校准，两者都保留在协议内。
- **单帧串行 vs 每线程一个 runtime**：一个 `JSRuntime` 不是线程安全的，多帧并发要么每条 binder 线程各持一个 runtime（堆限 × 线程数，「进程总量」的含义就此丢掉），要么串行化。选串行：解析路径本身是顺序的（读一本书的章节、聚合搜索里单源内部），瓶颈在网络不在 CPU，并行度收益远低于失控的内存记账风险。代价是多本书/多源并行时执行器是串行点，而且一条 binder 线程在最坏情况下被一次外呼占住（受超时上界约束，且因串行而恒为 1 条）。

## 被拒方案

- **第三方 QuickJS 绑定库**：接入最省事，但绑定层维护面单薄且是安全关键路径上的信任黑盒；自集成后内核（冻结稳定）与桥接（自有可审计）都无单点依赖。
- **androidx.javascriptengine**：官方且自带进程沙箱，但实现由 Google Play services 提供，无 GMS 设备上沙箱不可用——对国内市场设备等于不可用。
- **主进程内直接执行**（目标生态的原生做法）：防护只剩绑定层约定与逐源开关，原生漏洞直达业务进程，与仓内既有安全姿态冲突。

## 遗留

- CPU 时间计量（wall-clock 之外的进程级 CPU 监控）后续版本补。
- 网络 URL 白名单的宽松度按真实源失败率调校（过严会断内容站点的 CDN 引用）。执行器落地后「可解析 host」改为从源规则原文导出（导入侧没有字段可声明域名清单），导出规则偏严的可能没有改变——调校数据就是拒绝日志。
- **白名单与私网拒绝目前只覆盖脚本自己发起的外呼**：`java.ajax`/`load`/`post`/`responseCode` 一律经主进程的守门客户端，而 URL 选项 `js` 改写出来的地址仍由取文层按原路径发出（不查白名单、不判私网，与声明式 URL 同形）。把取文层并进同一条守门是后续项：并进去之前，脚本借 `js` 选项能到达的地址只受「主进程发得出这个请求」约束，不受白名单与私网判定约束。
- **会话罐是一源一份、只在内存里**（2026-09-12 随 `cookie` 面落地）：`SourceCookieJar` 同时挂在守门客户端与脚本的 `cookie.getCookie/setCookie/removeCookie` 上（必须是同一个实例，否则脚本读不到外呼攒下的会话），随源 parser 实例进 LRU、被逐出即丢，**不落盘**——应用重启后第三方站点的会话全丢。它与上一条同形：只覆盖脚本这一路，声明式取文不带罐。真要落盘，动手前得先定三件事（存的是第三方凭证：明文还是加密、清理入口归谁、唯一键用什么——`bookSourceUrl` 用户可改），逐条判据与症状预告写在规格 §11-37。
- **并发度未调校**：单帧串行是当前的锁形选择，实测卡在它（聚合搜索多源并行时执行器成串行点）再改成「每线程一个 runtime」，改的是客户端与桥接层的持有方式，协议与 JS 侧不变。
- WebView 内执行脚本（目标格式的 webJs 机制）不支持，属脚本书源解释器的延后项。
