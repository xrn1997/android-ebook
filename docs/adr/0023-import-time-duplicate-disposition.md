# 重复书目的处置收拢到导入时点，判重口径为 comment_key 主键

本 ADR 决定三件互相牵连的事：

1. **重复检测的时点**：从"书架加载后两两扫描 + SnackBar 轻确认"改为"**导入时点拦截**"——待导入文件的标题+作者算出 `comment_key`，与书架每本书的**当前主键**比对，命中即弹处置框。书架侧的被动扫描整条链（`BookMergeScorer` 五信号打分、`DuplicateBookDetector.scan()`、`BookListViewModel` 的建议通道与 `acceptMerge`、`BookRepository.mergeBooks`）**删除**。
2. **判重口径**：只认键相等（`CommentKey.compute` 归一化书名+作者），**不做模糊打分**。原 §9.4 的章名 LCS / 段落指纹 / 章数三档阈值随之撤销。
3. **导入页与详情页的顶栏形态**：`ImportBookActivity` 不再自绘 `TopAppBar` 与整页水平滑入滑出，改走基类 `BaseMvvmActivity` 的 Toolbar；`CAppTransparentTheme`（`windowIsTranslucent` + 透明窗背景）随之下线，四份 manifest 统一改用 `@style/ToolbarTheme.BackBar`。

## 背景

M2 交付的书架侧提示是"**事后 nag**"：书目已经在书架上了，才在进书架时弹一条 SnackBar 问要不要合并。这次做导入时点拦截之后，两件事同时暴露：

- **入口重复且更差**。重复是在导入那一刻被创造的；同一个判断在导入时点做，用户手里正拿着那个文件、处置意图明确；在书架时点做，用户得先回想"这两本是不是同一本"。两条链并存后，书架侧那条被删了调用方，留下 `BookListViewModel` 三个零调用方的成员与一份仍声称"由 BookShelfPage 调用"的 KDoc。
- **模糊打分在导入时点没有输入**。`BookMergeScorer` 的强信号是章名序列相似度与段落指纹，两者都要求**先把书切完章**。而导入前判重必须发生在切章之前——切一遍 2000 章的文件只为判断"是不是同名书"，代价与收益不成比例。剩下的书名+作者两个中信号，恰恰就是 `comment_key` 的两个输入项：既然精确键已经算了，模糊打分是在用概率方法重做一件已有确定解的事。

## 决策

### 1. 判重只认主键，且必须认主键

`DuplicateBookDetector.findMatchesFor` 比的是 `book_group` 里 `is_primary = 1` 那一行的 `comment_key`，**不是** `book_info.name`。两条理由都是硬的：

- **键含作者**（§9.1）。只比书名会把"同名不同作者"判成同一本书，而判重命中即给出会删条目的处置——误判一次的代价是删掉另一本无辜的书。保守方向与正文分页那条"宁漏页不串章"一致：**宁可漏提示，不可误并**。
- **主键正是修键面板维护的那一行**（§9.3）。比主键意味着用户改过匹配名之后检测自动跟随；比显示书名则两边脱节——面板改 `match_name`、检测读 `book_info.name`，用户改了名却仍然被当成另一本书。

作者解析两边不一致时算出不同键 → 不判重。这是刻意的漏报。

### 2. 处置动作四个，非破坏的那个占主按钮位

| 动作 | 语义 | 破坏性 |
| --- | --- | --- |
| 继续添加 | 两个条目共存，同键 → 评论读并集天然共享 | 无 |
| 智能合并 | 新条目多出的**尾部章节**补进旧条目，旧条目 `noteUrl`/进度/键全保留，新条目退场 | 低（只删新导入的那本） |
| 覆盖 | 新条目替换全部命中旧条目；删每一本之前先把它的 `book_group` 行吸收进新条目 | 高（旧条目进度作废） |
| 跳过 | 不导入本文件，继续处理下一个 | 无 |

- **"继续添加"是 spec §6 原本要求的出路**（"要看现有条目还是继续添加"）。缺了它，跨来源共存这套模型的主场景反而无法表达——用户只能在"毁掉一个"和"合并"之间二选一，而 §9 整套 `comment_key` + `book_group` 并集存在的理由就是让同一作品的多个来源并存。
- **顺序一律"先导入、后处置"**。反过来（旧实现的"先 `removeFromShelf` 再 `import`"）一旦导入抛异常（切不出章节、严格解码失败），旧条目已毁、新条目没进来，用户两头空。
- **覆盖必须先 `absorbGroupKeys`**：`book_group` 行随书删（`removeFromShelf`），旧条目身上可能挂着它自己历次合并攒下的 secondary 键，不先吸收就连读并集一起丢。
- **`mergeTailChapters` 只补尾、不插中间**，判据是"旧书归一化章名序列是新书的前缀"。前缀分叉说明两本切分规则不一致，按位置补章会把正文错位插进旧书，此时整笔放弃（返回 `Diverged`，两本共存）。补章目标必须是本地书——网络书的正文在书源那边，没有可补的载体。索引取现有最大 `durChapterIndex + 1`，不用 `size`（历史删章留下的洞会让 `size` 与末位索引不等，从而覆写既有章文件与同 `content_ref` 的行）。
- 暂停门用 `AtomicReference`，`getAndSet(null)` 了结：门由 IO 线程置入、主线程取出，普通 `var` 无跨线程可见性保证；一次性取出同时让连点天然幂等，不会把上一个文件的决策灌给下一个文件。

### 3. 顶栏回到基类，`CAppTransparentTheme` 下线

`ImportBookActivity`/`BookDetailActivity`/`module_find` 的 `SearchActivity` 原先挂 `CAppTransparentTheme`（透明 + translucent 窗），是为了配合旧的整页水平滑入滑出转场。透明主题与 Compose 基类的 Toolbar/insets 装配叠在一起后，页面自行接管顶栏的成本高于收益：

- 导入页改由基类 Toolbar 出标题与返回箭头，整页滑入滑出动画与 `finish()` 的退场拦截删除（转场回落成系统默认）。
- 详情页为一颗"编辑匹配信息"按钮自绘 `Scaffold + TopAppBar` 的做法**回退**：`ToolbarLayout` 没有 actions 插槽，自绘整条顶栏要连带接管返回箭头、状态栏 insets、容器配色，漏一项就是静默缺陷（实测已漏过一次返回箭头）。修键入口落到详情页正文底部的 `TextButton`。
- 资源侧 `lib_book_common/res/values/styles.xml`（`CAppTransparentTheme` 唯一定义处）随引用清零一并删除。

## 权衡

- **放弃模糊匹配**：同名不同作者、或作者解析结果两边不一致的两本同一书不再被提示。替代路径是修键面板人工归一（§9.3），以及处置后同键条目天然共享评论。被删的五信号算法与测试若要找回，得先解决"导入时点没有章名"这个输入侧障碍——这是本 ADR 认为不划算的部分。
- **同键共存不再是异常状态**：书架上同一作品出现多个条目是允许的（读并集共享评论），所以判重的目的从"消灭重复"降级为"告知并给出处置"，这也是非破坏动作占主按钮位的理由。
- **转场体验有损失**：导入页失去水平滑入滑出，与 ADR-0001 里"行为一比一移植"的表述在该页不再成立（阅读器、书评页仍成立）。
- **已知遗留（非本轮引入）**：覆盖与合并都会删条目，而 `BookRepository.removeFromShelf` 不清 `download_chapter` —— 这是「详情页 → 从书架移除」一直就有的行为（`DownloadRepository.deleteTasksForBook` 只被下载管理页调用），本轮没有把删除路径改窄，只是多了一个触发口。后果有界：那本书的章抓取必然失败，按 ADR-0018 的重试耗尽出队规则最终会离开队列。要根治应在 `removeFromShelf` 的调用侧统一收口（`download_chapter` 在 `lib_ebook_db`，仓库层归属不同，不宜由 `lib_book_common` 反向依赖 `module_book` 的下载仓库），单独一次改动处理。

## 验证

- `DuplicateBookDetectorTest` 锁判重口径：同书同作者命中、**同名不同作者不命中**、作者占位词两边归空、比对主键而非显示名（改过匹配名后检测跟随）、secondary 键不参与判重、多命中全部返回并按来源标注 `isLocal`。
- `BookRepositoryTest` 锁处置原语：`absorbGroupKeys` 吸收含 secondary 且不重复加同名键、`mergeTailChapters` 前缀对齐只补尾 / 序列分叉整笔放弃且不删新条目 / 索引有洞时接末位之后 / 目标是网络书时拒绝。
- `LocalBookImporterTest` 锁 `parseMetadata`：能拿到文件名里的书名作者、不写任何表、作者解不出时填显示用占位词。
- 变异自检（证明上述用例真守得住）：
  - 把 `findMatchesFor` 的口径退回"只比归一化 `book_info.name`" → 恰有 `同名不同作者不命中`、`比对的是当前主键…` 两条变红；
  - 把补章的下一索引退回 `oldChapters.size` → 恰有 `mergeTailChapters 旧书索引有洞时接在末位之后不覆写既有章` 一条变红，其余用例不受影响。
  - 两次变异均已还原，还原后 `./gradlew test :module_app:assembleRealDebug` 全绿（41 个测试类 0 失败）。
- **待人工装机验证**（Agent 止于编译与静态检查）：
  1. 导入与架上同书同作者的文件 → 弹四动作框；点"继续添加"后书架出现两个条目、两本都能看到同一批评论。
  2. 同作品但新文件结尾多出章节 → "智能合并"后旧条目章数增加、阅读进度不变、新条目消失。
  3. 章节命名不一致（如 `第1章` vs `第一章`）→ "智能合并"提示未补章、两本都在。
  4. "覆盖" → 旧条目从书架消失、新条目在架；命中项是网络书时框内不出现"智能合并"。
  5. 四个动作逐个走一遍后继续导入下一个文件（多文件选择时门不被上一个决策复用）。
  6. 详情页返回箭头存在、顶栏与书架/书城配色一致；导入页与书城搜索页在主题替换后状态栏观感正常（`windowIsTranslucent` 移除会改变启动转场观感）。
